## 1. 方案定位与结论

以 `bak/pos-app` 的业务页面、组件职责和示例数据为需求基线，建议沿用 `bak/pos-android` 的 Kotlin / Jetpack Compose 骨架实现后续 Android 原型。吸收最新 HTML 2.0 B 方案的桌台筛选、工作台信息组织和每桌草稿思路，形成一套能连续演示「选桌 → 开台 → 点餐 → 送厨 → 结账 → 清台 → 查单 → 交班」的 Android 平板原型。

本轮整理的是页面、交互、业务状态、组件映射、实施顺序与验收标准。后续原型采用本地模拟服务，不连接真实支付、厨房或门店后台。界面统一显示“演示环境”；模拟操作必须改变可查询的本地记录，不能只弹出成功提示。

### 1.1 交付边界

| 范围 | 本方案要求 |
| --- | --- |
| 核心使用者 | 堂食收银员；主管以授权身份参与；固定收银平板为主，窄窗和手持设备兼容 |
| 首轮业务 | 堂食多桌、开台人数、菜品与规格、草稿、送厨、挂起/恢复、现金与模拟扫码、支付查询、待清台、订单历史、模拟班次 |
| 首轮运行形态 | 可重置的本地演示数据；可模拟失败、离线、缺纸；旋转、切页、重启可恢复业务数据 |
| 后续扩展 | 换桌、并台、拆单、退款、优惠券、套餐换菜、完整会员、外带/外卖、真实外设及后台 |
| 首轮不纳入 | 商用支付接入、生产权限系统、跨设备并发、真实财务结算、打印机驱动、KDS、应用商店发布 |

设备型号、外设协议和门店促销规则尚未提供；不影响方案评审，进入真实设备实施前另行核对。本文标为“建议”“默认”的内容是本次设计选择，不是用户已确认的门店规则。

### 1.2 技术路线比较

| 路线 | 可复用内容 | 需要承担的工作 | 本次建议 |
| --- | --- | --- | --- |
| A. 扩展现有 Compose 骨架 | 五个页面、原生布局、规格弹窗、主题、基础控件 | 重整订单状态、持久化、模拟服务及异常流程 | **推荐**。已有原生基础，适合验证 Android 触控、窗口和生命周期 |
| B. 继续 uni-app 并补 Android 打包 | Vue 页面、样式、部分状态逻辑 | 补 App 构建链，验证原生打包、存储、返回键及外设桥接 | 多端同源优先时再选；当前 package scripts 只有 H5、小程序和类型检查，不能视为 APK 已就绪 |
| C. 延续 HTML 2.0 浏览器原型 | 最新桌台与点餐界面、快速视觉比较 | 仍需另做 Android 原生交互与业务状态验证 | 保留为视觉参照，不作为本轮 Android 落地基础 |

## 2. 现有代码能做什么，不能做什么

以下“已有”指静态代码中存在对应实现；本轮未重跑 H5、Android 模拟器或 APK。旧 README 和历史截图只作为参考，不能替代当前构建证据。

| 领域 | pos-app 现状 | pos-android 现状 | 整理后的目标 |
| --- | --- | --- | --- |
| 页面框架 | `PosShell` + 五页路由，L1–L6、1000px 窄屏断点 | `PosApp` / `FrameLayout`，960/1280dp 自定义断点 | 统一页面语义，以应用可用窗口决定布局 |
| 点餐 | 分类、搜索、标签、加菜、数量、待下单/已下单 | 增加规格、详情大图、滑删、图文/文字模式 | 按商品规格与备注区分订单行，限制库存，错误就地反馈 |
| 多桌 | 全局单张 A03 订单；桌台点击不绑定对应订单 | `switchTo()` 只换桌号/人数/时长；`openTable()` 清空共享菜品 | 按 `orderId` 管理完整订单；桌台仅关联当前活动订单 |
| 送厨 | 将所有待下单行改为已下单 | 同样改状态并显示离线/缺纸提示 | 送厨批次、发送结果、打印结果分开；可重试且不重复 |
| 结账 | 金额不足拦截；确认后 Toast，页面声称自动送厨但未实现该流程 | 按钮直接设 `paid = due`，无支付请求/查询；完成页退出时 `settle()` | 持久化支付尝试，覆盖处理中、未知、成功、失败 |
| 桌台释放 | 开台及清台等多为占位入口 | `settle()` 直接改为空闲并清订单行 | 支付成功后待清台；显式清台后空闲；历史订单保留 |
| 订单/挂单 | 静态列表，取单和补打等为提示 | `MockData.orders` 静态列表，`hold()` 只提示 | 列表与当前业务同源；可恢复挂起订单并查支付/送厨记录 |
| 交班 | 固定汇总、输入实盘；提交仍是提示 | 汇总和实盘均为固定示例 | 当班收款汇总、盘差说明、交班快照和下一班状态 |
| 设置/恢复 | 显示设置写入 uni 存储；订单在内存 | 主状态在 ViewModel；未见业务持久化 | 设置、业务记录和临时 UI 状态分层保存 |

证据入口：[Vue 订单状态](../bak/pos-app/src/stores/order.ts)、[Vue 桌台](../bak/pos-app/src/pages/tables/index.vue)、[Vue 结账](../bak/pos-app/src/pages/checkout/index.vue)、[Android PosStore](../bak/pos-android/app/src/main/java/ai/neargo/fnb/pos/state/PosStore.kt)、[Android 结账](../bak/pos-android/app/src/main/java/ai/neargo/fnb/pos/ui/checkout/CheckoutScreen.kt)、[Android 订单](../bak/pos-android/app/src/main/java/ai/neargo/fnb/pos/ui/orders/OrdersScreen.kt)、[Android 交班](../bak/pos-android/app/src/main/java/ai/neargo/fnb/pos/ui/shift/ShiftScreen.kt)。

### 2.1 吸收最新 B 方案的范围

保留桌区/状态/桌号组合筛选、菜品搜索和标签、桌台详情、菜品列表独立滚动、操作栏固定，以及“有待下单菜品时送厨为主操作”的方向。

不移植 iframe 注入、替换全局渲染函数、字符串替换按钮、父窗口高度减固定数值等实现方式。B 方案的会话内每桌草稿只是交互参照，不能作为 Android 持久化订单模型。其“未加载账单被显示为空订单”的限制需要在新原型中明确消除。详见 [B 方案交接](全线点餐POS-B方案交接.md)。

## 3. 信息架构与页面结构

主导航保持四项：**桌台、点餐、订单、交班**。结账是携带 `orderId` 的任务页面，不提供无账单上下文的独立入口。设置、网络、打印从系统栏进入；会员先作为订单内的绑定入口。

建议启动时先检查演示班次：未开班显示开班入口；已开班默认进入桌台。选择进行中的订单后进入点餐。空上下文的“点餐”引导选择桌台，不默认为 A03。首轮隐藏外带/外卖切换，避免只换标签而不改变业务。

### 3.1 页面清单

| 编号 | 页面 | 核心区域 | 主操作与返回 |
| --- | --- | --- | --- |
| P00 | 开班 | 收银员演示身份、收银台、备用金、演示说明 | 开班进入桌台；未开班禁用新增收款 |
| P01 | 桌台 | 桌区、统计/状态筛选、桌号搜索、桌台网格、详情 | 空闲桌“开台”；用餐桌“继续点餐”；待结账“去结账”；待清台“清台” |
| P02 | 点餐 | 分类、搜索/标签/视图、菜品网格、账单 | 有草稿“送厨”；无草稿且有应收“去结账”；切页保留草稿 |
| P03 | 结账 | 账单核对、优惠摘要、应收/已收/待收、支付方式、操作区 | 发起支付；返回保留订单与支付尝试，不删除记录 |
| P04 | 收款结果 | 结果、桌号/单号、金额、方式、找零、打印任务 | “完成，返回桌台”；失败/未知提供相应处理入口 |
| P05 | 订单 | 状态筛选、搜索、订单列表、详情及时间线 | 未结账打开；挂起恢复；已结账查看/模拟补打 |
| P06 | 交班 | 当班流水汇总、备用金、应有/实盘/差异、未完业务 | 核对并交班；差异必填说明；支付中/未知未解决时阻止完成 |
| P07 | 设置与设备 | 显示、模拟网络、厨房/打印状态、演示数据管理 | 保存设置；重置演示需确认且不在支付处理中执行 |

### 3.2 平板默认布局

建议 L1 为默认：分类/桌区在左，内容居中，账单/详情在右；L3 为次要验收布局：横向分类 + 左侧账单。现有 L2/L4/L5/L6 保留为高级布局候选，首轮不扩展其功能，不承诺未经验证的组合全部可用。

```text
┌ 门店 / 班次 ─ 桌台 · 点餐 · 订单 · 交班 ─ 网络 · 打印 · 设置 ┐
│ 分类/桌区 │ 页面标题 · 搜索 · 筛选/视图 │ 桌号 · 人数 · 单号 │
│           │                            │ 待下单             │
│ 可滚动    │ 菜品 / 桌台 / 订单列表     │ 已下单             │
│           │ 独立滚动                   │ 独立滚动           │
│           │                            ├ 金额摘要           │
│           │                            │ 次操作 / 主操作    │
└───────────┴────────────────────────────┴────────────────────┘
```

系统栏、账单底栏固定；页面标题不占多行大面积说明。账单先显示菜品和待收金额，费用明细可展开。菜品网格和账单分别滚动，长账单不推走送厨/结账按钮。页面标题、动作和状态统一中文，保留资源化接口。

### 3.3 窄窗布局

分类变为横向筛选；主列表占满可用宽度；底部摘要显示“当前桌 · 件数 · 待收金额”，点击打开账单。账单作为有独立滚动区的底部面板；不足以容纳键盘、金额和操作时改为全屏任务页。底部摘要必须位于应用导航上方，键盘出现时不被遮挡。

## 4. 页面交互规格

### 4.1 桌台

1. 桌区、状态、搜索同时生效。统计基于选中桌区、应用状态/搜索前的桌台集合；列表旁另显示筛选后的数量，避免统计语义变化。
2. 桌台卡显示桌号、容量/人数、状态、时长和未结金额。金额读取同一份订单数据；加载中显示“账单加载中”，失败显示“加载失败，重试”，不能显示 ¥0.00 冒充空账单。
3. 空闲桌开台弹出人数选择，默认座位数、可修改；输入须为正整数，超过容量提示确认。成功后创建新订单并进入点餐。
4. 已预订桌经“确认到店”进入人数确认；用餐中或待结账桌打开关联订单；停用桌不能开台。
5. 收款完成只转为待清台，详情可查看刚完成的账单；“确认清台”清除桌台活动关联，历史订单仍可查。
6. 首轮换桌、并台、拼桌入口隐藏；文档及组件样张保留后续位置，不用点击成功提示伪装已完成。

### 4.2 点餐与账单

| 触发 | 行为 | 保护/异常 |
| --- | --- | --- |
| 搜索 | 跨分类按菜名/编号匹配；清空后回到此前分类；标签继续参与过滤 | 无结果显示清空筛选入口；拼音首字母列为后续能力 |
| 点击普通菜 | 添加一份，更新账单和当前桌金额 | 沽清不可加；限量校验在状态层执行，不能仅显示“剩 N” |
| 点击规格菜 | 显示规格组、必选标记、加价、数量、合计；确认后加菜 | 每个商品使用自己的规格定义，不共用一套固定规格 |
| 重复加菜 | 同商品、规格 ID 集合、备注、价格快照且为待下单时合并数量 | 不并入已送厨行；显示名相同不能作为合并键 |
| 修改草稿 | 加减、备注、删除；删除提供短时撤销 | 已下单不能直接删除或改价，后续由授权退菜处理 |
| 切换桌台 | 保存当前草稿，读取目标桌活动订单 | 会员、优惠、备注、支付尝试一并隔离；不复用全局数组 |
| 挂起/恢复 | 保存订单并标记挂起，回到桌台；从订单页恢复 | 堂食挂起不释放桌台；挂起不等于取消 |
| 送厨 | 创建当前草稿行的批次，显示发送中，成功后转已下单 | 同一批次连点或重试不重复生成厨房任务 |

送厨按钮明确计数单位，例如“送厨 · 2项 / 5份”，不混用行数和数量。操作栏最多一个主按钮：有待下单时“送厨”，无待下单且有未付金额时“去结账”。首轮默认先送厨后结账；若还有草稿，结账入口提示先送厨，不沿用 Vue 页中未实现的“收款后自动送厨”。外带先付后制的流程另行设计。

规格、备注、开台人数为短任务弹窗；退款和组合支付等后续复杂任务使用独立页面，避免多层弹窗叠加。

### 4.3 结账与收款结果

进入结账时固定 `orderId`、订单修订号与计价快照，核对菜品、服务费、会员优惠、抹零和待收金额。支付处理中/结果未知时该订单锁定金额编辑；返回其他页面不会解除锁定。

首轮开放现金、模拟微信、模拟支付宝。银行卡、会员储值和组合支付暂不开放实际流程；不得沿用“银行卡不需要网络”的演示判断作为产品保证。

| 支付状态 | 显示内容 | 允许动作 |
| --- | --- | --- |
| 待支付 | 当前待收、方式说明；现金显示实收和找零 | 选择方式、发起支付；现金不足禁用确认 |
| 支付中 | 当前交易号、金额、“等待付款结果” | 查看进度；禁止重复发起；可返回账单查看但不能改金额 |
| 结果未知 | “尚未确认是否到账，请先查询” | 查询原交易；禁止再次收款或直接标失败 |
| 明确失败 | 失败原因及交易号 | 确认失败后可创建新的支付尝试 |
| 已支付 | 成功金额、方式、实收/找零、单号、打印状态 | 完成返回桌台、查看订单、模拟补打 |

模拟扫码必须能选择成功、明确失败、超时未知三个场景；未知场景的查询可返回成功、失败或仍未知。离线禁止新建扫码支付，现金可在本机记账。现金确认以本地事务保存支付记录与订单结果，双击不得增加第二笔收款。

支付成功即更新订单、桌台和班次流水，不等待用户离开成功页。小票失败只影响打印任务；成功页显示“已收款，小票打印失败”，不把支付改成失败。再次进入成功页或重启不能重复结账。

### 4.4 订单与交班

订单筛选包含进行中、挂起、待结账、支付待确认、已结账、已取消。支付待确认是支付记录派生的筛选项，不复制一套互相矛盾的订单状态。选中项被筛选移除后清空详情，不能继续显示上一张订单。

订单详情包括菜品快照、费用、送厨批次、支付尝试、打印记录、关键操作时间线。补打生成带原订单引用的新打印任务；首轮不开放退款/反结账，只展示后续扩展说明。

交班汇总来自当前班次成功支付记录，支付未知不计成功收入但进入待处理清单。演示应有现金 = 开班备用金 + 现金净收；首轮不开放钱箱支出和退款，后续加入时要扩展公式。差异 = 实盘 − 应有，非零必填说明并生成模拟主管审批记录。

已送厨未收款订单可交接给下一班，并随交班快照保存；含未送厨草稿时，须选择保留并交接或返回处理。支付中、支付结果未知、未完成送厨请求和待审批盘差均阻止完成交班。支付尝试创建时绑定当前 `shiftId`，成功流水沿用该归属；交班提交与新支付创建互斥，并在提交事务内重新检查阻塞项。成功后旧班次只读，新建班次后恢复收款；交接过来的未付款订单，其下一次新支付归属新班次。

## 5. 状态模型与一致性规则

### 5.1 必须分开的对象

| 对象 | 最小字段与职责 |
| --- | --- |
| Table | `tableId / zoneId / seats / status / activeOrderId / lastClosedOrderId`；桌区是显式字段，不从桌号推断 |
| Order | `orderId / tableId / status / guests / memberId / remark / revision / lines / pricingSnapshot / openedAt` |
| OrderLine | `lineId / dishId / optionIds / remark / quantity / unitPriceMinor / status`；保存成交菜名与规格快照 |
| KitchenBatch | `batchId / orderId / lineSnapshots / status / operationId`；只提交本次新增菜品 |
| PaymentAttempt | `attemptId / orderId / shiftId / revision / method / amountMinor / status / idempotencyKey / providerRef`；现金另存实收/找零 |
| PrintJob | `jobId / sourceId / kind / status / retryCount / reprintOf`；厨房单与收款单分开 |
| Shift | `shiftId / operatorId / openedAt / floatMinor / closedAt / countedMinor / varianceReason / handoverSnapshot` |
| OperationRecord | 操作 ID、对象 ID、时间、结果及演示操作者；支持追踪重试和重放 |

金额统一用最小货币单位的整数；Android 建议 `Long`。显示层负责格式化，不用二进制浮点直接累加货币。商品单价与计价规则随订单快照保存，修改菜单不会追改历史账单。

### 5.2 核心流转

```text
桌台：空闲 → 开台/待点餐 → 用餐中 → 待结账 → 待清台 → 空闲
      已预订 → 确认到店/开台

订单：进行中 ⇄ 挂起；进行中 → 待结账 → 已结账
      仅空订单或无送厨/支付记录的草稿可取消；其余取消首轮不开放

菜品：待下单 → 发送中 → 已下单
                ├ 明确失败 → 待重试（仍属于未成功送厨）
                └ 结果未知 → 核对原批次，不新建重复批次

支付：待支付 → 支付中 → 已支付 / 明确失败 / 结果未知
      结果未知 → 查询 → 已支付 / 明确失败 / 仍未知

打印：排队 → 打印中 → 已打印 / 失败；失败可重试
```

开台后无菜品为待点餐；有草稿或已下单菜品为用餐中；进入结账任务转待结账，取消结账且无进行中的支付尝试可回用餐中。已结账后加菜必须新建订单，不复用已关闭订单。

“已下单”不等于“已打印”，也不等于厨房已制作。在首轮模型中，它表示模拟厨房服务已接受该批次。网络离线时保存待发送任务并显示“待送厨”，不声称已经送达厨房。若未来通过局域网厨房打印实现离线接单，须按真实设备回执另加可验证路径。

### 5.3 不可违反的业务约束

1. 首轮一桌最多一张活动订单；一次切桌同时切换所有订单上下文。
2. 桌台详情、点餐账单、结账、订单历史使用同一个订单来源；未加载、加载失败、空订单必须是三个不同 UI 状态。
3. 业务命令在状态/领域层校验；隐藏按钮不能代替限制。已下单行不可调用普通减数量删除。
4. 同一订单同一时刻只有一个进行中或结果未知的支付尝试；相同请求重试返回原结果。
5. 支付成功记录、订单已结账、桌台待清台、班次流水原子更新；金额和状态同时发布给 UI。
6. 打印失败不撤销收款；送厨失败不丢草稿；重启不把未知支付自动当成失败。
7. 示范服务费 10%；绑定演示会员后优惠为菜品小计的 5%；抹零默认关闭，启用时最后抹去不足 1 元部分。计价方式沿用现有 mock 便于对照；仅为演示参数，不是已确认的门店计价政策。

金额基准例：菜品小计 ¥200.00，服务费 ¥20.00，无会员时应收 ¥220.00；启用上述会员示例规则后优惠 ¥10.00，应收 ¥210.00；现金实收 ¥250.00，应找零 ¥40.00。费用明细、桌台金额、订单记录须一致。

首轮库存按单设备演示：草稿不占用其他桌库存；每次加菜检查当前可售量，送厨提交时再次检查并原子扣减。提交后库存不足保持原批次未成功状态，提示调整数量后生成新的有效提交；失败/未知重试不得再次扣减。多设备库存预占留待接后台设计。

## 6. Android 适配与视觉规范

### 6.1 窗口、密度和触控

按应用窗口与实际内容约束布局，不按设备名称或物理像素定版；宽度、可用高度、系统栏和软键盘都参与布局。Android 官方推荐以窗口尺寸分类组织自适应界面；本文的 960/1280dp 是延续项目的 **POS 自定义布局阈值**，不是官方 WindowSizeClass 枚举定义。[官方窗口尺寸说明](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)

| 可用内容宽度 | 默认呈现 | 详情与内容规则 |
| --- | --- | --- |
| < 600dp | 单列任务、横向分类、底部摘要 | 账单全屏或面板；结账单列；商品按实际空间排 1–2 列 |
| 600–959dp | 宽主内容 + 详情面板 | 商品通常 3–4 列；不强塞三栏 |
| 960–1279dp | 分类 + 内容 + 账单 | 账单建议 320dp，分类 88–96dp；内容不足时分类转顶部 |
| ≥ 1280dp | 完整三栏 | 账单建议 360–400dp，默认 380dp；超宽增加内容列数，限制卡片宽度 |

表中列数是预期范围，不是硬编码值；按卡片最小宽度与间距计算。建议菜品卡最小 144dp、桌台卡最小 128dp。内容可用高度小于 480dp 时优先压缩系统摘要、减少固定头部，复杂任务全屏滚动，确保金额与主操作可达。

默认采用标准密度：常规触控区域至少 48×48dp、主操作高度建议 56dp；紧凑模式仅减少间距与非交互区域，不把相邻点击目标压缩到互相重叠。现有 36/44 的控件视觉尺寸不能直接成为触控目标。正文建议 16sp，辅助文字 14sp，金额 28–32sp；使用等宽数字。触控下限依据 [Compose 无障碍默认行为](https://developer.android.com/develop/ui/compose/accessibility/api-defaults)，其余数值是本方案设计建议。

### 6.2 视觉收敛

首轮只验收一套默认主题：白色面板、浅灰背景、松绿主色、标准密度，图文/文字两种菜品视图。建议主色采用 v1.6 的 `#306F5F`、选中浅底 `#DFF2EC`、正文 `#181A1C`，通过 Android 语义 token 映射，不在每个组件中写色值。

| 语义 | 表现 |
| --- | --- |
| 主操作 | 松绿实心，每个任务区域一个；次操作浅灰底 |
| 当前桌/订单 | 主题浅底 + 描边；保留业务状态自己的图标和文字 |
| 选中规格/支付方式 | 主题浅底 + 勾选标记，不仅依赖颜色 |
| 待下单/挂起 | 使用“暂存”状态语义；正文明确待下单，不用深浅猜测 |
| 待处理/未知 | 待处理状态语义 + 明确动作入口 |
| 错误 | 异常状态语义 + 错误原因 + 重试/处理入口 |

视觉来源有冲突时，本方案优先：布局采用本文，选中和主操作取 v1.6 方向，业务状态分组取 [业务状态](全线点餐POS-业务状态.md) 的九组语义。旧 v1.6 中“预约/暂存都用灰色”等规则不继续覆盖最新状态表。状态表由生成脚本维护，不直接手改生成文档。

现有多主题、深色模式和玻璃效果保留为后续展示能力；默认原型不依赖模糊效果或支付彩带传递结果。状态使用图标+文字；TalkBack 读出桌号、状态、金额及按钮动作，长按/滑动动作提供可见替代入口。文字放大时控件可增高，不裁掉关键金额和状态。

### 6.3 返回键、软键盘与恢复

- 返回顺序：关闭键盘 → 关闭当前浮层 → 返回上一任务页；根页面遵循系统返回行为，已保存业务不因返回而清空。未提交的规格选择关闭时不写入账单。
- 支付处理中/未知时返回可离开页面，但交易仍在订单记录中持续可见；回到该订单只能查询/等待，不能重复收款。
- 搜索只占用当前页面输入焦点；现金数字键盘为应用控件，避免同时弹出系统键盘。扫码枪输入需要独立接入点，不默认写入当前搜索框。
- 使用系统 inset 与键盘可用空间；固定操作栏不能压住手势区域。旋转与分屏只改变布局，不重新创建订单或触发收款。
- UI 筛选、当前对象 ID、滚动位置用可恢复状态；业务订单、支付和任务队列持久化到本地数据库；显示偏好独立存储。ViewModel 本身不能保证进程被回收后的业务恢复。[官方 Compose 状态保存说明](https://developer.android.com/develop/ui/compose/state-saving)
- 原型自动保存已确认的加菜/数量/备注修改；写入失败显示错误并保留未保存标记，不提示保存成功。重启先恢复本地数据，再核对未完成支付/送厨任务。

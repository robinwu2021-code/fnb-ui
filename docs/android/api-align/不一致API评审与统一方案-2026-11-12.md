# POS ↔ 餐饮服务端：不一致 API 逐条评审（2026-11-12）

> 原则：**默认按后端统一**；POS 现有做法明显更合理的，标「建议后端采纳 POS」并写理由；双方都说得通、取决于业务口径的，标「需双方确认」。
> 后端依据 = 代码（`/biz/x/food`）为主，代码与 POS 合同草案（`docs/api/pos-fnb`）不一致时单列。配套：`餐饮服务端与POS接口对齐-2026-11-12.md`。

裁定记号：**后端** = POS 改；**POS** = 建议后端改；**确认** = 需双方定；**后端内部** = 后端自身不一致，POS 按适配层结果走。

# 离线 / 在线 / 局域网 切换方案

## 1. 两个维度，不是三种模式

| 维度 | 取值 | 现状 |
|---|---|---|
| 设备角色（门店内） | 单机 / 主 POS / 副 POS | 已有（`LanRole`），手动设置 |
| 云端连通 | 在线 / 离线 | 只有系统网络检测和「强制离线」开关，云端未接 |

组合出的实际状态：

| 状态 | 门店内权威 | 云端 | 典型场景 |
|---|---|---|---|
| 单机 · 在线 | 本机 | 主 POS 角色的同步适配回放到云 | 小店一台收银机 |
| 单机 · 离线 | 本机 | 进待同步 | 断网营业 |
| 主 POS · 在线 | 主 POS | 主 POS 回放到云 | 多台收银 / 点餐平板 |
| 主 POS · 离线 | 主 POS | 进待同步 | 外网断、内网通 |
| 副 POS · 连上主机 | 主 POS（副机发意图） | 副机不直连云 | 点餐平板、第二收银台 |
| 副 POS · 主机失联 | — | — | 只读，提示「主 POS 未连接」（已实现） |

**原则**：第一期门店内永远以主 POS（或单机）为准；云端只接收回放、下发菜单等主数据。这样内网断开、外网断开、两者都断都能分开处理。

## 2. 云端连通的判定

| 项 | 规则 |
|---|---|
| 探测 | 主 POS 每 30 秒请求一次轻量接口（`GET /store/info`），超时 3 秒；有正常业务请求成功也算一次心跳 |
| 判离线 | 连续 2 次失败，或系统报告无网络，或「强制离线」打开 |
| 判在线 | 连续 2 次成功（防止网络抖动来回切） |
| 退避 | 离线期间探测间隔 5 → 10 → 30 → 60 秒封顶；系统网络恢复时立即探一次 |
| 归属 | 只有主 POS / 单机探测云端；副 POS 显示主机转发来的云端状态 |

## 3. 各状态能做什么

| 功能 | 在线 | 云离线（内网通） | 副 POS 主机失联 |
|---|---|---|---|
| 开台、点单、送厨、本机出厨房单 | ✅ | ✅ 进待同步 | ❌ 只读 |
| 现金 / 刷卡收款 | ✅ | ✅ 本机记账，进待同步 | ❌ |
| 扫码收款、储值、积分、会员查询 | ✅ | ❌ 提示「离线不可用」 | ❌ |
| 退菜、赠送、折扣（主管授权） | ✅ | ✅（本机授权，进待同步） | ❌ |
| 厨房屏、打印 | ✅ 局域网 | ✅ 局域网 | — |
| 菜单 / 价格修改 | 走云端发布 | 只允许沽清、临时下架 | ❌ |
| 日结签署 | ✅ | ❌ 要等同步完 | ❌ |
| 交班 | ✅ | ✅ 本机出交班单，进待同步 | ❌ |

## 4. 状态切换时做什么

**在线 → 离线**
1. 正在发的请求：结果未知的**不重建**，留在待同步，等恢复后按幂等键查结果（草案约定「超时先查结果」）。
2. 界面：页头云图标变「离线 · N 条待上传」；依赖云端的按钮置灰并写原因（复用 `DeviceStatus.readOnly` 那套）。
3. 扫码收款进行中 → 提示改用其他方式或稍后查结果，不自动重扣。

**离线 → 在线**
1. 先查「结果未知」的请求（按幂等键），再按命令日志顺序回放待同步；回放期间页头显示「同步中 n / N」，营业不中断。
2. 回放完再拉增量：菜单新版本（`revision` 变了才拉）、云端产生的订单（小程序 / 扫码点餐，第二期）。
3. 冲突（10409 版本冲突）：拉最新 → 按本机意图重放一次 → 仍冲突进「需处理」列表（同步页已有），不阻塞后面无关的命令（按订单分组，同一张单的命令保持顺序）。

**主 POS 失联（内网）**
- 副 POS 只读（已实现），本地草稿保留（购物车草稿已实现）。
- 第二期：主机长时间不回来时，由店长在一台副 POS 上「接管为主 POS」（`authorityEpoch` 递增，旧主机回来后自动降为副机并交出未同步命令）。

## 4.1 实时推送（服务端 `feat/store-push-sse`，契约 `docs/api/push.openapi.json`）

服务端已做「终端登记 + 门店通知 + 定向消息 + 回执」，接入方式：

| 步 | 接口 | POS 做法 |
|---|---|---|
| 登记 | `POST /biz/push/terminals`（`installId`、`clientType=POS`、`platform`、`appVersion`）→ 端号 | **只有主 POS / 单机登记并订阅**；`installId` 用本机设备 ID（同一安装重复登记返回同一端号）。换人登录会换绑、未送达定向消息作废——POS 员工 PIN 换人不应触发重新登记（仍是同一终端账号） |
| 订阅 | `GET /biz/stores/{storeNo}/push/stream`（SSE，带端号） | 只在**在线**状态连接；离线时断开，恢复在线后重连。通知帧 `PushFrame{seq, topic, refType, refNo, refVersion}` **只带对象号和版本**，内容按现有接口重读 |
| 定向消息 | `DirectedFrame{messageNo, kind, payload, expireAt}` | 打印唤醒 → 触发打印网关；配置重载 → 拉菜单 / 门店策略新版本；升级 → 提示。过期的丢弃 |
| 回执 | `POST /biz/push/acks`（批量 ≤ 100） | 处理完再回执（状态只往前走）；未确认的消息重连时服务端重发，POS 按 `messageNo` 去重 |

与切换方案的关系：
- **推送是在线状态的增量通道**：恢复在线后先回放待同步、再连 SSE；SSE 断开不等于离线（仍以第 2 节心跳判定），只降级为定时轮询重读。
- **门店内转发**：主 POS 收到通知后，经局域网把需要的变更（菜单新版本、配置重载）分发给副 POS 和厨房屏；副 POS、KDS 第一期不直连云端推送。
- **去重**：`refVersion` 不大于本机已知版本的通知直接忽略（POS 自己回放产生的变更也会推回来）。
- **已与后端确认**：员工 PIN 换人不重新登录终端账号、不重新登记，端号和名下消息不受影响；换绑只在同一 `installId` 用另一个登录身份重新登记时发生。**主 POS 切换门店后必须先重新登记再订阅**（带端号订阅时门店须与登记时一致，否则返回 400）。

## 5. 离线的边界（防止离线太久）

| 项 | 规则 |
|---|---|
| 离线授权 | 已有：短期 7 天 / 长期 90 天，到期暂停营业写入 |
| 待同步上限 | 超过 2000 条或最早一条超过 24 小时：页头告警；超过 72 小时：禁止日结，提示联网 |
| 时钟 | 已有回拨检测；回放时以服务端 `acceptedAt` 为准，本机时间只作参考 |

### 8.2 影响离线方案的一点

平台幂等表声明保留 **24 小时**（目前事实上长期有效，但不是契约）。本方案 §5 允许离线到 72 小时才禁止日结，超过 24 小时的回放没有幂等保证。两条路，**需后端决定**：
1. 开台、员工下单各加可选 `clientRef`（门店内唯一、永久、可按它查回服务端单号）；
2. 后端书面承诺幂等记录保留期 ≥ POS 离线上限，并开放「按幂等键查结果」的读接口。

在后端定之前，§5 的 24 小时告警（POS 尚未实现）文案定为「超过 24 小时的离线数据补传可能重复，请尽快联网」。

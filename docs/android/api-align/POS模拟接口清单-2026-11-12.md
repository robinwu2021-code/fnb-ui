## 0. 结构总览：「模拟 API」到底是什么

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 仓库接口（即模拟 API） | `core/data/Repositories.kt` | ViewModel 只依赖这些接口。注释原文：“当前实现为完整离线的本机仓库（LocalWorkspace）；阶段三接服务时替换实现，保持接口与错误语义不变”（`Repositories.kt:25-29`）。 |

## 1. 通用约定

### 1.1 金额
- 全部用 `Long` 整数**分**，不使用浮点（`core/model/Money.kt:3-9`）。
- 币种：`Money.CURRENCY = "CNY"`，`SUPPORTED = {CNY}`（`Money.kt:11-12`）。门店设置里有 `currency` 字段，结账时会校验（`DiningService.kt:97`）。零售侧按地区处理币种属于另一套逻辑，这里没有细查。
- 上限：单价/加价 `MAX_UNIT = 9_999_900`（¥99,999.00），单行份数 `MAX_QTY = 999`，单据/收款/备用金 `MAX_BILL = 9_999_999_999`（`Money.kt:13-18`）。
- 比例：服务费、会员折扣用**万分比**整数（`serviceBp` 0–2000，`memberBp` 0–5000，`Models.kt` StoreSettings），四舍五入（`Money.rate`）。主管整单折扣用 `percent` 1–100（100 = 原价）；活动折扣用 `percent` 50–99（`LocalWorkspace.kt:601`）。
- 订单在开台时保存费率快照（`TableOrder.serviceBp/memberBp`），之后改门店设置不影响已开的单（`DiningService.kt:81`）。
- **【对齐】** 收款方式是中文字符串常量：`"现金" "扫码" "银行卡" "储值卡"`（`DiningService.kt:99`，`LocalWorkspace.kt:898`），没有枚举码。

### 1.2 时间
- 全部是 `Long` 毫秒时间戳，取自客户端 `clock()`（默认 `System.currentTimeMillis`）。
- 命令信封里，`occurredAt` 是客户端时间，只用于展示；`acceptedAt` 和门店序号由协调方生成（`CommandJournal.kt:19-23`、`:53-54`）。
- 授权模块会记录 `lastSeenWall`，用来检测时钟回拨（`LocalWorkspace.kt:107-108, 324`）。

### 1.3 ID
- 生成方式：`newId(prefix) = "$prefix-<UUID>"`（`LocalWorkspace.kt:383`），全部由客户端生成。
- 前缀一览：`O` 订单，`TS` 桌台会话，`R` 预订（另外结账单打印任务也用 `R`），`P` 收款，`H` 挂单票，`A` 调整审计，`K-<storeId>` 送厨批次，`M` 会员，`MT` 会员流水，`D` 日结（开钱箱打印任务也用 `D`），`DC` 日结单打印，`S` 交班记录，`SH` 交班单打印，`E` 员工，`area`/`c`/`g`/`m` 分别是区域/分类/规格组/餐牌，`SM` 库存流水，`B` 预结单，`RP` 补打，`V` 退菜单，`FB` 厨房屏改打纸单，`T` 测试页和任务日志，`s` 门店。
- **桌号 `tableId` 是用户输入的业务码**（`^[A-Za-z0-9-]{1,8}$`，大写，`ManageRules.kt:19-21`），同时作为 `StoreData.orders` 这个 Map 的 key。订单本身有稳定 `orderId`，换桌时保留（`DiningService.kt:153-156`）。**【对齐】** 大部分接口用桌号定位订单，不用 orderId。
- 订单行 `uid` 是门店级递增的 `Long`（`StoreData.seq`），不是 UUID（`DiningService.kt:200, 282`）。**【对齐】** 多机或云端生成行 ID 时要另外定规则。
- KDS 任务卡 ID：只有一个档口时等于批次号；多个档口时是 `批次号@档口`（`DiningService.kt:312`）。
- SKU key 由排序后的 `组ID:选项ID` 拼成，用 `|` 分隔（`Models.kt:20-22`、`ManageRules.kt:68`）。
- 设备 ID `dev-<UUID>`，首次启动生成（`LocalWorkspace.kt:187`）。`tenantId` 固定为 `"local-tenant"`（`Vault`，`:94`）。

### 1.4 幂等与命令 ID
- 每次带事件的写入生成一个 `JournalCommand`（`CommandJournal.kt:25-42`），字段有：`storeId, deviceId, commandId, type, payload(JSON 字符串), aggregates[{id, expected}], tenantId, actorId, correlationId(=commandId), coordinatorId, authorityEpoch, occurredAt, schemaVersion=2, payloadVersion=1, authorizationRef(授权 jti), policyVersion`。
- 本机命令的 `commandId` 是新 UUID。副机意图由主机执行时，沿用副机的 `deviceId/commandId/actorId`（`LocalWorkspace.kt:333-336`，`RemoteOrigin` 见 `:162`）。
- 幂等范围是 `storeId + deviceId + commandId`。摘要用 SHA-256 计算，不包含 `authorizationRef/policyVersion`。同 ID 同内容时返回原回执；同 ID 不同内容时拒绝（`CommandJournal.kt:73-77, 104-110`）。
- 回执 `JournalReceipt{status: Committed|Rejected|Conflict, eventId, revisions, result, acceptedAt, sequence}`（`CommandJournal.kt:47-58`）。Rejected 和 Conflict 都是终态，同 ID 重放得到同样结果。
- 送厨批次号 `batchId` 和收款 ID 同时是 `OutboxItem.id`，注释说它们是“幂等键”（`Models.kt` OutboxItem 注释，`OrderRules.kt:83-86`）。
- 副机意图在发送前先持久保存为 `PendingIntent`，超时后用同一 `commandId` 重发；主机执行前先查 Inbox 去重（`LanLink.kt:115-157`，`RemoteIntent.kt:84-86`）。
- `CommandOutbox` / `CommandDispatcher` / `LoopbackTransport`（`CommandOutbox.kt`）是持久发送端，状态机为 Saved → Sending → Committed/Rejected/Conflict/Waiting/Expired，失败后按 1s 到 60s 指数退避。**主代码没有使用它，只有 `androidTest/.../CommandJournalTest.kt` 引用。** 这是为云端或主机传输预留的。

### 1.5 聚合与版本
- 聚合划分见 `Aggregates.kt:5-8`：Order、TableSession（按桌台）、Reservation、Catalog、StockLedger（按商品）、Shift。代码里实际使用的 ID 有：
  - `order:<orderId>`、`table:<tableId>`、`reservation:<id>`：页面事件由 `Aggregates.page()` 根据前后快照差异算出（`Aggregates.kt:15-28`），目标桌排在最前，作为主聚合。
  - `member:<id>`：用储值卡结账时追加（`DiningService.kt:89-91`）；会员建档和充值也用它。
  - `catalog`：所有门店配置，包括档口配置。`stock:<productId>` 用于盘点。`shift` 交班，`day` 日结，`staff` 员工，`kds:<ticketId>` 加 `table:<tableId>` 用于 KDS。零售用 `retail`、`stock:*`、`drawer`。
- 一个命令可以涉及多个聚合（换桌、并台、拆单、到店开台），这些聚合在同一事务里一起校验版本，任何一个冲突就整笔拒绝（`Aggregates.kt:5-8`，`CommandJournal.kt:113-121`）。
- **【对齐】** 期望版本 `expected` 取自本机 `Vault.aggregateRevisions`（`LocalWorkspace.kt:330-332`），不是 UI 层传入的“所见版本”。所以单机下基本不会出现 Conflict。仓库接口里只有 KDS 的 `expectedRev` 由调用方传入。
- 命令日志表：`command_aggregates`（版本）、`command_inbox`（回执）、`command_events`（`sequence` 自增、`acked` 标记、`envelope`）、`command_scope`（门店对应的租户、协调方和 epoch）（`CommandJournal.kt:185-200`）。

### 1.6 写入的通用前置条件（`LocalWorkspace.transaction`，`:313-349`）
1. 启动恢复失败时（`blocked`），拒绝一切写入。
2. 带事件的写入：副 POS 直接拒绝，提示“副 POS 不直接写入业务数据，请经主 POS 执行”；授权不可写时（离线授权过期、撤销等）也拒绝。
3. 权限检查：`StaffRules.permFor(eventType)` 把事件类型映射到权限点（`core/model/Staff.kt:45-67`）。没启用员工模式时，门店账号按店长处理。远端命令按副机当班员工校验（`LocalWorkspace.kt:447-457`）。
4. 业务 `check` 返回中文原因，方法返回 `Result.failure(IllegalStateException(原因))` 或 `OrderResult.Rejected(原因)`。**【对齐】** 只有可展示的中文文案，没有错误码。

### 1.7 离线行为（三种“队列”要分开看）
| 名称 | 位置 | 内容 | 现状 |
| --- | --- | --- | --- |
| 演示同步队列 `StoreData.outbox: List<OutboxItem>` | `Models.kt` OutboxKind/OutboxItem | 只有两类：`Kitchen`（离线送厨批次）和 `Payment`（离线收款） | `syncNow()` 是**模拟补发**：把所有门店的 Pending 项直接标为 Done，`ackSource="simulation"`；送厨批次的 Queued 行改为 Sent；收款标为 `synced=true`（`LocalWorkspace.kt:974-1001`）。不发网络请求，也不写事件。由 `SyncEngine` 在“联网且有待同步项”时自动调用（`AppContainer.kt:122-137`）。 |
| 云事件队列 `command_events.acked=0` | `CommandJournal.kt:170-181` | 所有带事件写入产生的事件 | 云端没有接入，所以从来不 ack。界面显示“云端未接入 · N 条事件在本机”。 |
| 副机待确认意图 `LanState.pending` | `LocalWorkspace.kt:144-159`，`LanLink.kt` | 副机发给主机的命令 | 已经能在真实局域网上运行。 |

- **【对齐】** 是否在线由 UI 用 `online: Boolean` 参数传进来（`settle`、`sendToKitchen`），实现不自己探测网络。离线时：送厨的行变成 `Queued`，同时入队一个 Kitchen 项，但**厨房单仍然立刻在本机出单**（`DiningService.kt:304-321`）；收款入队一个 Payment 项，记录 `synced=false`；`扫码` 在离线时被拒绝（`DiningService.kt:101`）。
- 只要还有 `Queued` 行就不能结账（`OrderRules.kt:130-136`，`CheckoutPolicy.BLOCK_WHEN_CLOUD_PENDING = true`，`:154-156`，状态为“待门店确认”）。
- 只在主机上能做的：配置、库存、交班、日结、打印、建会员、充值、活动配置、送达确认（见 `Routed.kt`）。

## 4. 局域网协议：RemoteIntent（副 POS → 主 POS）

- 传输：TCP（默认端口 47600）。握手用 ECDH P-256，双方用设备私钥签名整段握手，HKDF 派生两把 AES-256-GCM 密钥，nonce 严格递增防重放（`LanChannel.kt:25-31`）。配对码 8 位，5 分钟有效，最多尝试 3 次（`LanHost.kt:31`）。协议名 `neargo-lan-v1`。
- 请求帧 `LanRequest{id, kind, storeId, commandId, actorId, payload, token}`，响应帧 `LanResponse{id, ok, message, result: IntentResult?, token, store?}`（`LanHost.kt:26-27`）。`kind` 有：
  - `ping`
  - `command`：`payload` 是 RemoteIntent JSON（判别字段 `kind`），返回 `IntentResult{ok, message, qty, duplicate}`
  - `snapshot`：返回整份 `StoreData` JSON；`token` 是 sha256，相当于 ETag，没变化时不带 body。副机用它替换本店的只读副本（`LanLink.pull`）
  - `kds-pull`：`token` 是游标，`payload` 是档口
  - `kds-ack`：`payload` 形如 `"id:rev,id:rev"`
- 主机执行（`RemoteIntent.kt:74-148`）：用 Mutex 串行执行；先核对门店一致，再按 Inbox 去重；在 `RemoteOrigin` 上下文里调用本机仓库，所以命令日志以副机的设备、命令 ID 和操作人记录；执行后恢复主机自己的选桌。
- 副机结果回传：成功后会主动 `pull` 一次快照；零售类操作通过 `message` 带回单号或时间戳。

## 5. 设计文档对云端契约的承诺

来源：`docs/architecture/同步节点与事件契约.md`（2026-11-10 架构草案，“尚未实现”）和 `docs/architecture/多POS离线局域网与云端协同方案.md`（同日草案）。

1. **拓扑与权威**：门店营业命令由当前主 POS（StoreCoordinator）串行确认。云端负责身份、授权、配置版本、事件副本和对账，**不直接改进行中的订单**；云端后台对进行中订单的操作也要路由给主 POS（协同方案 §1，契约 §1）。首期不做多主写入，也不用整份 StoreData 覆盖其他终端。
2. **命令信封（逻辑字段，尚未定 HTTP/WS）**：`schemaVersion, commandId, tenantId, storeId, deviceId, actorId, coordinatorEpoch, authorizationRef, aggregateType, aggregateId, expectedRevision, type（例如 AddOrderItems）, correlationId, occurredAt（ISO 字符串）, payload`（契约 §4）。主机接受后生成 `eventId`、`causationId=commandId`、`aggregateRevision`、`storeSequence`、epoch、接受时间和规则版本。
   - **与代码的差异**：代码是 `aggregates[]` 多聚合列表、`authorityEpoch`、`occurredAt` 为毫秒 Long、`schemaVersion=2`；文档是单个 aggregateType/Id/expectedRevision，epoch 叫 `coordinatorEpoch`。事件类型命名也不同：文档例子 `AddOrderItems` 是命令名，代码里 `type` 用的是事件名 `DishAdded`。
3. **幂等**：范围 `storeId + deviceId + commandId`，保存请求摘要和原结果；同编号不同内容拒绝；事件按 `eventId` 去重；厨房任务用稳定的逻辑任务 ID；补打每次用新的尝试 ID 并关联原任务（契约 §4）。代码已经实现这些。
4. **版本冲突**：返回当前版本和差异；可以安全合并的加菜重新校验后生成新命令；结账、退款、并台不自动覆盖（契约 §4、§6）。
5. **确认分层**：`localCommitted / storeCommitted / kitchenDelivered / kitchenProgress / cloudCommitted / paymentState` 各自独立；打印另有 `sentUnverified/confirmed/failed/unknown`（契约 §3）。
6. **同步与游标**：握手交换身份、协议版本、授权、epoch、快照版本和已提交游标；先用水位 W 的一致快照，再接 W 之后的增量；本地事务提交后才推进游标；**云端导入的历史事件不能再次触发打印、收款或送厨**；对账覆盖订单、支付、库存流水和任务数；删除用带版本的墓碑；遇到鉴权失败、版本不兼容或金额冲突，进入处理队列，不无限重试（契约 §5）。
7. **业务规则承诺**：配置变更以云端或管理端版本为准，已点的行保留价格和规格快照；全局券、跨店储值、线上支付默认必须在线；在线支付结果未知时先查询，不能重复收款；交班快照不能被之后的同步静默改写（契约 §2、§6）。协同方案 §6 **建议放宽** queued 时不能结账的规则：门店已提交且厨房交付达到条件时，允许现金结账，即使云端不可达。这条“待确认”，代码现在仍然阻止。
8. **凭证**：CloudAccessToken 15 分钟（建议）、Refresh、DeviceIdentity、OfflineGrant（短期 7 天、长期 90 天，用户已确认）、LanSession（例如 8 小时）、LocalSession（例如 12 小时）。OfflineGrant 包含 `iss/sub/aud/jti/iat/nbf/exp, tenantId, storeId, deviceKeyThumbprint, roles/scopes, policyVersion, authEpoch, offlineUntil`，以及委托范围和深度（协同方案 §5）。
9. **未确认项**：到期宽限、首次离线注册的营业权限、失联副 POS 临时单、厨房交付条件、离线资产额度、支付方式和设备型号（协同方案 §8）。

## 6. 先前项目的契约：`/Users/workingowl/work/app/pos/contracts`

- 文件：`openapi/pos-api.yaml`（984 行），`messages/envelope.schema.json`，`messages/types/{command,notify,data-changed}.schema.json`。README 说明这里是“端云契约唯一真源”，Android 端的 DTO 由测试校验必须与 yaml 一致；破坏性变更要升级 `/v{n}`。

- **结果**：`accepted{idempotencyKey, serverOrderNo?, rejectedLines{行id→原因码}, pickupNo?}`，或 `rejected{idempotencyKey, code}`。这里用的是**机器可读的原因码**，例如 `sku_sold_out`、`pin_wrong`、`token_expired`。

## 7. 对齐服务端时要注意的问题（汇总）

1. **云端协议还是空白**：没有任何 HTTP 或云端调用；`syncNow` 是模拟；`command_events` 从不 ack；`CommandOutbox/CommandTransport` 没有接到主流程。可以直接把 `CommandTransport{query(command), submit(command)}` 当作云端接口的骨架。
2. **事件载荷是状态快照**（整单、整桌、受影响桌），而且同一事件类型可能来自不同语义（例如 `OrderMemberChanged` 同时用于 setMember 和 bindMember，`OrderBenefitsChanged` 同时用于 setBenefits 和 setPromotions）。部分载荷信息不全，例如 `ProductsRepriced` 没有 ids，`KitchenSubmitted` 不带 KDS 卡，零售载荷普遍只有摘要。服务端要先决定：只接收事件作为归档，还是要求命令可以重放。
3. **定位与 ID**：用桌号定位订单，订单行用门店自增 `uid`，所有 ID 由客户端用 UUID 生成；`orderId` 已经有了，但接口签名没有用它。
4. **错误语义**：只有中文提示文本，没有错误码；结账靠 `amount == 本地重算的 due` 防止账单变化，没有订单版本号。
5. **在线状态由调用方传入**（`online` 参数），离线收款和送厨各有自己的队列和阻止结账规则；扫码和充值的离线规则不一致；收款方式是中文常量；储值和会员都只在门店本地（跨店储值的在线要求没有实现）；主管凭据会经 LAN 意图传输；体验账号的主管密码写死在代码里（`LocalWorkspace.kt:666, 866`）。

# 餐饮服务端与 POS 接口对齐（2026-11-12，第一版）

> 依据三份清单：
> - 服务端：餐饮服务端 API 清单（只在本地整理，不入库；来源 ai-shop `backend-plugins/shop-industry-food`，分支 `claude/food-channel-menu-445679`，55 个 Biz 控制器 / 261 个端点）
> - POS：`POS模拟接口清单-2026-11-12.md`（同目录，`bak/pos-android` 的仓库接口 78 个、事件 54 个、局域网意图 27 个，餐饮部分）
> - 服务端已有的 POS 合同草案：见服务端仓库（ai-shop `docs/api/pos-fnb`，42 条固定路由，**自称后端未实现**）
>
> 本文只做对齐分析与方案，不改两边代码。标 **【待后端】** 的需要后端确认或补接口。

## 一、结论（先看这里）

1. **两边的基本模型不同**：POS 第一期是「本机为准、离线先行」——主 POS 是门店权威，命令写本地日志，云端从未接入（`syncNow` 只是本地标完成）。服务端是「在线为准」——购物车 → 报价 → 确认 → 下单批次，价格由服务端算，写入靠版本号和幂等键。**不能把 POS 仓库接口一对一换成服务端调用**，要加一层「云端同步适配」。
2. **对接目标用服务端的 POS 草案（42 条），不直接对 261 个原接口。** 草案正好是 POS 需要的那一层：固定路由、只用 GET/POST、`storeNo` 显式传、统一幂等和版本。原接口粒度细（报价哈希、白名单 query、严格拒绝未知字段、两种门店定位），由后端适配层消化更合适。草案目前没实现，需要后端排期。
3. **三个硬缺口，没有它们 POS 不能真正上云**：
   - **结账写入【待后端】**：Biz 侧只有 `GET /settlements/{no}`，收银（现金 / 刷卡 / 扫码 / 储值、拆付）无入口；草案里有 `/checkout/preview|confirm|result`，但未实现。
   - **现金交班【待后端】**：库里有 `fnb_cash_shift` 表，没有接口；草案也没有。
   - **会员 / 储值 / 优惠活动**：餐饮插件里没有，在平台域；草案也没有，需要另定。
4. **约定层面多数能对上**：金额都是最小单位整数（POS 要补 `currency`），单号都是字符串。要改的是：幂等键用 POS 已有的 `commandId`、收款方式改枚举码、错误按 `code` 而不是中文文案判断、时间格式待抓包确认。

## 二、通用约定对照

| 项 | 服务端（代码） | 服务端 POS 草案 | POS 现状 | 对齐做法 |
|---|---|---|---|---|
| 地址 / 版本 | `/biz/x/food/...`，无版本段 | `/pos/fnb/...` 固定路由 | 无 | 适配层只认草案路由；草案落地前不直连原接口 |
| 认证 | 商家 Bearer token；操作者由服务端取 | 同左，另有 `/auth/login`（account+password+terminalNo） | 本机账号 + 员工 PIN + 离线授权 | 终端登录换 token；员工 PIN 只在本机，操作者映射为终端账号 + `staffNo`【待后端：员工身份怎么带】 |
| 门店 | 路径 `storeNo` 或请求头 `X-Store-No` | body/query `storeNo` | `StoreData.id`（`s-uuid`） | 门店 ID 映射表（本机 id ↔ `storeNo`），建店 / 认领时建立 |
| 信封 / 错误 | `{code,msg,data}`，业务错误 HTTP 200 | 同左 | 失败只有中文提示，无错误码 | 适配层按 `code` 分类（10409 冲突 → 重读、10400 → 校验错、网络 → 重试），中文文案只用于展示 |
| 幂等 | 请求头 `Idempotency-Key`（≤128） | body `idempotencyKey` | 命令 `storeId+deviceId+commandId` + SHA-256 摘要 | **幂等键 = 本机 `commandId`**（同一命令重放永远同键同内容）；位置以最终实现为准【待后端：头还是 body】 |
| 并发 / 版本 | body `version`（读来的），桌台 `tableVersions`，报价 `confirmationDigest` | `version` + `quoteHash` | 本地聚合版本（订单 / 桌台 / 预订），结账靠「金额等于重算应收」 | 每个服务端对象的 `version` 存进映射表；冲突 → 拉最新再按本地意图重放一次，仍冲突进人工处理 |
| 金额 | `xxxMinor:long` + `currency` | 同左，`Amounts` 7 字段 | `Long` 分，只 CNY，费率用万分比 | 金额一致；请求补 `currency`；服务费 / 会员价以服务端报价为准（见四.3） |
| 时间 | 混用 Instant / LocalDateTime / OffsetDateTime / String | 未写 | `Long` 毫秒 | 统一转毫秒；`LocalDateTime` 字段按门店时区解释【待后端：Instant 实际格式，抓包确认】 |
| ID | `xxxNo` 字符串（≤32），服务端生成 | 同左 | 客户端 `前缀-UUID`；订单行 `uid` 是门店自增 Long；订单按桌号定位 | 用已有的 `StoreData.idMappings` 记「本机 id ↔ 服务端 No」；订单改按 `checkNo` 对外，桌号只做显示 |
| 枚举 | 大写字符串，服务端白名单 | 同左 | 收款方式是中文常量；状态是 Kotlin 枚举 | 收款方式改码：`CASH / CARD / QR / STORED_VALUE`；状态双向映射表（见五） |
| 严格入参 | 249 个 DTO 拒绝未知字段 | 未写 | — | 每个接口单独请求模型，禁止共用带多余字段的通用 DTO |

## 四、对齐方案

### 4.1 分层：在 POS 加一层「云端同步适配」，界面和业务服务不改

```
界面 / ViewModel ─ 仓库接口（不变）─ DiningService 等（本机为准，不变）
                                         │ 命令日志（已有：commandId + 聚合版本 + 事件）
                                         ▼
                          CloudSync 适配（新）：按事件类型翻译成草案接口调用
                                         │ Idempotency = commandId；映射表 idMappings
                                         ▼
                          服务端 POS 合同（草案 42 条，后端实现，映射到 /biz/x/food）
```

- 只在**主 POS**运行（和打印网关一样），副 POS 不直连云。
- 按命令日志顺序逐条回放；一条失败就停在这条（同店有因果顺序），网络错误退避重试，业务错误（10400 / 10409）进「待人工处理」列表，展示在现有同步页。
- 服务端返回的 `xxxNo`、`version` 写进 `StoreData.idMappings`；后续命令引用本机 id 时由适配层换成服务端号。

### 4.2 事件 → 服务端调用映射（第一批，覆盖主流程）

| 本机事件 | 服务端调用（草案） |
|---|---|
| `TableOpened` | `/table/open` |
| `KitchenSubmitted` | `/cart/create`（每单首次）→ `/cart/line/save` ×N → `/pricing/quote` → `/order/submit` |
| `TableChanged` / `TableMerged` / `OrderSplit` | `/table/transfer` / `/table/combine` / `/check/split/confirm` |
| `DishVoided` | `/return/create` |
| `PaymentRecorded` | `/checkout/preview` → `/checkout/confirm`（等后端） |
| `DayClosed` | `/close/preview` → `/close/sign` |

**本机事件要补的数据**（盘点发现）：`KitchenSubmitted` 不带 KDS 任务卡和行明细；`ProductsRepriced` 没有商品 ids；打印配置、人工确认送达、`syncNow` 改业务数据却不产生事件。适配前先补齐事件载荷。

### 4.3 价格以谁为准

- 菜单价从云端已发布菜单拉取 → POS 本机算价和服务端报价**同源**，正常情况下一致。
- 服务费、会员折扣、满减：POS 现在本机按万分比算；上云后以服务端报价为准，本机算价只用于离线和展示；回放时报价金额与本机不同 → 记差异，结账时按服务端应收。

### 4.4 离线

- 第一期继续「本机为准」：开台、点单、送厨（本机出单）、现金 / 刷卡收款都能离线完成，进命令日志等回放。
- 扫码收款、储值、会员这些依赖云端的，离线拒绝（现状已如此，充值离线未拦截要补）。
- 冲突（离线期间云端改了同一张单，如小程序加菜）：第一期门店只有 POS 写，冲突概率低；出现 10409 时进人工处理，第二期再做自动合并。

## 五、状态映射（第一批）

| 对象 | POS | 服务端 |
|---|---|---|
| 桌台 | 空闲 / 用餐中 / 待清台 / 已预订 / 已结账 | `turnoverState` IDLE / IN_USE / NEEDS_CLEANING（预订、已结账服务端无，本机保留） |
| 订单行 | New / Queued / Sent / Rushing / Served | 购物车行（新加）→ 批次行；上菜由厨房任务 READY / 交付推导【待后端确认】 |

| 收款方式 | 现金 / 扫码 / 银行卡 / 储值卡（中文常量） | 改为码 `CASH / QR / CARD / STORED_VALUE`，与平台收款域对齐【待后端确认码值】 |

## 六、需要后端确认 / 补的（按优先级）

1. **结账写入**：POS 草案 `/checkout/*` 何时实现；现金 / 刷卡「外部记账」怎么记。
2. **POS 合同草案**整体排期（42 条适配到 `/biz/x/food`）；幂等键放请求头还是 body。
3. **现金交班接口**（`fnb_cash_shift` 已有表）。
4. **员工身份**：POS 员工 PIN 上岗后，操作者怎么带给服务端（`staffNo` 头？终端账号？）。
5. **赠送 / 主管折扣 / 会员 / 储值 / 活动**归哪个域、怎么调。
6. **时间格式**：Instant 实际输出（毫秒还是 ISO）；`LocalDateTime` 字段的时区。

**需处理的两个动作**：服务端按幂等键固定业务结果，同键重试只会拿到同样的拒绝。所以「重试」= 人工确认原因已排除后用新尝试键 `事件ID#n` 重传；「跳过」= 人工已在后台处理，本机标记为已处理不再上传。处理前该订单后续事件暂停上传，其他订单不受影响。

**模拟器端到端（pos_tablet）**：开台、换桌上传后约 1 秒到服务端，服务端桌台状态与本机一致；服务端连续 503 时页头转「离线（HTTP 503）」，恢复后自动补传；服务端桌台被占时进「需处理」，页头红点，重试后成功；需处理在应用重启后保留。日结只有单测，没有在模拟器上跑（本机需先全部结账，结账还没接服务端）。

## N2-01 命令与事件信封

`JournalCommand` 升级为信封 v2，主要字段如下：

| 类别 | 字段 |
| --- | --- |
| 协议 | `schemaVersion`=2、`payloadVersion`=1、`type` |
| 作用域 | `tenantId`、`storeId`、`deviceId`、`actorId` |
| 关联 | `commandId`、`correlationId`；causationId 即 commandId |
| 并发 | `coordinatorId`、`authorityEpoch`、`aggregates`（参与聚合及各自期望版本） |
| 传输凭据 | `authorizationRef`、`policyVersion` |
| 时间 | `occurredAt`，客户端时间，仅供展示 |

**校验规则（`CommandJournal`）**
- **直接拒绝，不写回执：** 以下情况属于来源无法确认，不产生任何回执。
  - 不支持的信封版本或载荷版本。
  - 缺少作用域字段，或参与聚合为空或重复。
  - 与门店登记的租户、协调方或 epoch 不一致。门店的首条命令会登记到 `command_scope`。
- **幂等：** 摘要覆盖业务内容和作用域，不含授权字段，所以刷新传输凭据不改变摘要。同 ID 不同内容会被拒绝。
- **终态回执：** 回执分为 Committed、Rejected、Conflict 三种，都写入 Inbox。同 ID 重放时返回原结果。
  - Conflict 会逐个列出冲突的聚合，以及期望版本和当前版本，便于定位。
  - Rejected 由处理器抛出 `CommandRejected` 产生。
- **事件行：** 新增 `envelope`、`accepted_at`、`causation_id`、`correlation_id` 四列。旧事件的 envelope 为空，即 legacy。
- **聚合状态列：** 不再写占位值，改为记录聚合类型、最后事件、最后命令。

**本机身份**
- 设备 ID 在工作区创建时生成，随首次保存落盘，此后不变。
- tenant 暂为 `local-tenant`，actor 为当前登录账号。
- 这些身份都来自本机上下文，N4 之前不是可信身份证明。

## N2-02 聚合与稳定 ID

**稳定 ID**
- **订单号：** 开台时生成 `TableOrder.orderId`。换桌时订单号保留。
- **桌台会话号：** 开台时生成 `DiningTable.sessionId`。换桌时目标桌开新会话，清台完成后会话号清空。
- **并台：** 目标订单记录 `mergedOrderIds`。
- **拆单：** 目标订单沿用已有订单号或新生成一个，并记录 `splitFromOrderIds`，不把拆单当作并台。
- **收款：** `PaymentRecord.orderId` 记录所属订单。旧收款为 null，表示关联未知，不按桌号推断。

**聚合划分（`Aggregates`）**

| 聚合 | 命名 |
| --- | --- |
| 订单 | `order:<orderId>` |
| 桌台 | `table:<tableId>` |
| 预订 | `reservation:<id>` |
| 目录 | `catalog` |
| 库存 | `stock:<productId>` |
| 交班 | `shift` |

- **跨桌操作：** 换桌、并台、拆单、预订到店一次参与多个聚合，在同一事务中全部校验版本，任一冲突就整笔拒绝。
- **版本镜像：** 各聚合版本存在 `Vault.aggregateRevisions`，与命令日志在同一事务提交。冲突回执不会推进本地版本。
- **旧单流：** `page-order-stream` 只作为旧流水位，不再写入，新事件不混入旧流。

**权威与读模型：** 本机仍是每店单写协调方，页面快照 `StoreData` 作为读模型，与事件在同一事务提交，不会各自成为权威。

**金额：** 已在后续的金额专项中统一为 Long 分，详见[金额专项实施记录](金额专项实施记录-2026-11-11.md)。

## N2-03 持久命令发送端

- **`SnapshotStore.saveCommand`：** 改为必须实现。旧 DataStore 适配器明确抛错，测试内存适配器显式声明能力（`testReceipt`）。
- **`CommandOutbox`：** SQLite 表 `command_outbox` 保存原请求、摘要、目标、状态、尝试次数、下次时间、最后错误和回执。
  - 状态：Saved → Sending → Committed / Rejected / Conflict。
  - 失败后回到 Waiting，按指数退避，从 1 秒到 60 秒。
  - 重启后，Sending 回到 Waiting。
  - 超过保留窗口的标为 Expired，不删除，也不当新请求重发。
- **`CommandDispatcher`：** 每条先查回执，未知时才用同一命令重投。测试覆盖了"已提交但回执丢失"，业务只执行一次。
- **`CommandTransport`：** 本机用 `LoopbackTransport`，直连本机日志。主机和云端传输在 N5、N8 实现同一接口。

## N2-04 迁移、恢复与异常

**数据库 v3 迁移**
- 支持从 v1 或 v2 升级，迁移在一个事务内完成。
- 新增 `schema_migrations` 表，记录版本、时间和说明，说明里写明旧事件条数和旧流最高版本。
- 损坏处理器改为保留原文件。系统默认的处理器会删库。

**旧数据**
- 活动订单补发订单号和会话号，映射写入 `StoreData.idMappings`，来源标为 legacy-v3。
- 已结账的历史记录不补订单号。

**坏库只读阻断**
- 恢复失败时，工作区的 `blocked` 非空。
- 此时所有写入被拒绝，模拟打印和同步也不执行，不会用演示数据覆盖原库。
- 页面显示全屏的「本地数据需要恢复」，不会进入工作台。

**备份与恢复（`LocalRecovery`）**
- **备份：** 用 `VACUUM INTO` 生成同一恢复点的完整副本，存在 `files/backups`。
- **原始导出：** 原样复制当前库，坏库也能导出，但这类副本不能用于恢复。
- **恢复步骤：**
  1. 在临时副本上打开并升级，完整校验。
  2. 保留当前库：正常时做一致性备份，坏库时原样导出。
  3. 替换数据库并重新加载。
- **入口：** 系统管理 → 设备与系统 → 数据与恢复。页面显示设备 ID、数据库版本、最新事件序号、未确认事件（含旧版数量）、未决发送命令、待同步队列、备份列表和迁移记录。恢复前会提示备份之后的数据缺口。

## 验证

- **单元测试：** 94 项通过，新增以下 9 项。
  - `CommandEnvelopeTest`，共 6 项：信封字段、重启后设备 ID 不变、开台的订单和桌台聚合、每个聚合独立的版本、换桌/拆单/并台的订单身份与多聚合、管理类聚合、冲突不改状态。
  - `CommandConcurrencyTest`，共 3 项：并发 6 条命令的版本连续、切店中提交仍落在原门店、坏库阻断后修复再解除。
- **设备测试：** 19 项通过。
  - `CommandJournalTest` 改写为 9 项：幂等与凭据不影响摘要、冲突和拒绝的终态回执、多聚合原子性、作用域/版本/epoch 拒绝、回滚、v1 和 v2 升级、重开后重放、发件箱重试与重启与过期。
  - 新增 `RecoveryTest`：备份 → 继续营业 → 恢复，确认事件与快照同一恢复点；坏库阻断 → 原始导出 → 从备份恢复。
- **模拟器：** 在 `pos_tablet` 上用旧的 v2 数据覆盖安装，验证了以下几点。
  - 升级记录为「旧事件 8 条为 legacy」，新的加菜事件挂在订单聚合下，并带有完整信封。
  - 重启后继续写入成功。
  - 在界面上备份并恢复，恢复前多出一份副本，恢复后还能继续写入。
  - 英文界面检查过。新增文案已补 37 条 en.json 词条。

## 开发中发现的缺陷

**设备 ID 生成时机：** 全新安装时，设备 ID 原本要到第二次启动才生成。第一次运行的命令会以「未分配」登记协调方，重启后设备 ID 一变，所有写入都会因协调方不一致被拒绝。现已改为创建工作区时生成，并有单元测试和设备测试覆盖。

## 仍未覆盖

- **发件箱：** 页面操作尚未经由发件箱，等 N5 有主机传输时接入。
- **身份与授权：** `authorizationRef` 和 `policyVersion` 没有真实的签发和校验，这属于 N4。
- **杀进程：** 只做了重启重开测试，还没有在写入过程中真实断电。
- **备份位置：** 备份只在本机应用目录。导出到外部存储或云端需要另定策略。

# Android POS · 多业态架构对齐（2026-11-12）

> 依据：《[端架构](../全线点餐POS-端架构.md)》（技术分层 · 业务模块 · 多业态 · 离线 · 多设备集群，在 `pos-react-retail` 分支）、《[零售业态接入方案](零售业态接入方案-2026-11-11.md)》、合并请求 robinwu2021-code/fnb-ui#2 的评审结果。
> 目标：零售合并进餐饮 App 之前，把「按门店业态切换」收成一处、两业态各走一套独立接口、公共部分抽出来只写一份；第一期只做全离线（单机 + 店内局域网，不依赖互联网）。

## 一、目标架构（与端架构文档对齐）

```
应用壳（PosApp）── 登录选店 → session.biz ─→ BizProfile.of(biz)   ← 唯一的业态切换点
   │                                         │
   ├─ 餐饮工作台（桌台 · 点餐 · 结账）        ├─ 零售工作台（收银 · 订单 · 商品 · 库存）
   │    └─ FloorRepository + OrderRepository  │    └─ RetailRepository（RetailService 实现）
   │                                          │
   └──────── 共用：系统管理 · 交班 · 报表 · 打印 · 客显 · 员工权限 · 会员 · 主副 POS ────────
                         │
              公共内核 StoreKernel（门店事务、权限、单号、库存账、打印副本、主管授权、收款入账）
                         │
              本地数据（LocalWorkspace：SQLite 快照 + 命令日志 + Outbox）── 局域网主副 POS
```

| 端架构文档的要求 | Android 落点 | 对齐前 | 对齐后 |
|---|---|---|---|
| 差异只放在「业态配置」一层 | `core/model/BizProfile`：页签、首页、系统管理菜单、打印路由、外设、报表 / 交班 / 门店设置口径、客显模式 | `if (biz == Retail)` 散在 20 处（导航、管理菜单、打印、报表、交班、客显、门店设置、商品列表） | 全部读 `BizProfile`，新增业态只加一个 profile |
| 两个业态插件 | 餐饮：`FloorRepository` + `OrderRepository`；零售：`RetailRepository` | 零售实现全写在 `LocalWorkspace` 里（2000+ 行，两业态混在一个类） | 零售抽成 `RetailService`，只依赖公共内核；`LocalWorkspace` 只委托 |
| 领域服务只有一套 | 公共流水线写一份 | 收款入账（收款记录、离线 Outbox、会员积分 / 储值流水）餐饮 `settle` 和零售 `checkoutRetail` 各写一份，已经出现不一致（换货退差价没退回会员储值） | `Settlement`：收款记录 + Outbox + 会员消费 / 退款，两业态共用 |
| 按网络状态做能力降级 | `RuntimeProfile`（第一期 = 全离线） | 线上订单（需要平台）、跨设备调拨（需要云）在界面上直接可用 | 第一期 profile 关掉依赖互联网的能力：线上订单入口隐藏，扫码收款按现有规则离线不可用；局域网主副 POS 保留（不依赖互联网） |

| 8 | 收款入账逻辑两业态各写一份 | 抽 `Settlement` | ✅ 已改，单测覆盖 |
| 9 | 收款校验里同一规则算两遍 | 改为逐条求值一次 | ✅ 已改，单测覆盖 |

## 四、第一期收尾联调（2026-11-12）

两台平板模拟器一主一副（`pos_tablet` 作主 POS，`pos_tab` 作副 POS，adb 端口转发模拟同一局域网），零售科技园店：

| 场景 | 结果 |
|---|---|
| 主机设为主 POS、生成 8 位配对码；副机填「IP:端口 + 配对码」配对 | ✅ 已连接（加密），会话 8 小时 |
| 副机扫码收款 | ✅ 单号由主机分配（#R0166），主机订单页同步出现 |

| 副机按原单退货（部分退） | ✅ 主机、副机都显示部分退货与退货记录 |
| 主机断开时副机收款 | ✅ 拒绝写入、购物车保留；主机恢复后自动重连，接着收款成功 |

联调发现并已修（另：餐饮未送厨的新加菜本来就写进门店账本，重启不丢，不需要草稿）：

| # | 问题 | 处理 |
|---|---|---|
| 1 | 主机断开时副机「确认收款」按钮照常可点，原因只在一闪而过的提示里 | 设备状态加只读原因 `DeviceStatus.readOnly`（由主副 POS 连接状态合成，`RoutedDevice`），零售收银、餐饮结账的确认按钮都直接显示「主 POS 未连接，本机只读」并置灰 |
| 2 | 收银台购物车只在内存：取回的挂单在 App 被杀后丢失（挂单已删、购物车没了） | 本机购物车草稿 `CartDraftStore`：每台设备、每家门店一份，存本机不进账本；变动即存，重启恢复并提示，收完或清空即删 |
| 3 | 配对对话框改对配对码后，旧的错误红字还挂着 | 改任一输入框即收起错误提示 |

单测 230 个通过（新增收银台草稿恢复 / 保存 / 收完删除、只读原因）。

## 七、本期不做（第二期）

- 餐饮业务实现同样从 `LocalWorkspace` 抽成 `DiningService`（接口已独立，实现搬迁风险大，单独排期）。

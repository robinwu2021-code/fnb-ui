# N6 网口 ESC/POS 打印实施记录

日期：2026-11-11。分支 `android-ui-v3`。按用户选择，对接通用网口 ESC/POS 小票机（RAW TCP 9100），不依赖厂商 SDK。

## 结论

打印链路已经实现，包括分级结果、档口路由、自动重试与人工核对，并用假 ESC/POS 打印机在单元测试和模拟器上验证过。**还没有用真实打印机核对**，见文末。

## 发送与结果分级（`core/print/EscPos.kt`）

**编码**
- 初始化 `ESC @`，开启汉字模式 `FS &`。
- 标题居中、倍宽倍高，正文用 GB18030 编码。
- 结尾走纸 4 行后切纸 `GS V B 0`。

**发送步骤：** 每张任务建立一个连接。
1. 用 `DLE EOT 4` 查纸张、`DLE EOT 1` 查脱机。
2. 写入打印数据。
3. 用 `DLE EOT 2` 查错误。

**结果分级**

| 情况 | 结果 | 处理 |
| --- | --- | --- |
| 连接失败；发送前缺纸、脱机，或打印机关闭连接 | 未发出 → **失败** | 确定没打，按退避自动重试（2 秒起，最长 60 秒） |
| 写入成功，随后状态正常 | **已发送 · 状态正常** | 只表示已写入打印机，**不等于确认出纸** |
| 写入成功，打印机不回状态（超时） | **已发送 · 未回状态** | 适用于不支持状态查询的型号，可在配置中关闭查询 |
| 写入中断开；发送后连接已关闭；发送后报开盖、缺纸或故障 | **结果未知** | 可能已经部分或全部打出，**不自动重打、不改投备用打印机**，必须人工核对 |

开发中修了一个误判：发送后查状态时，读到「连接已关闭」原本被当成「型号不回状态」，误记为已发送。现在改为结果未知，测试连续 5 次稳定通过。

## 网关与状态（`PrintGateway`、`LocalWorkspace`）

- **网关：** 只有主 POS 或单机领取任务，副 POS 不打印。流程是：领取任务并持久化为「发送中」→ 在锁外发送 → 回写结果。同一时间只发一张。
- **重启：** 重启时仍是「发送中」的任务改记为结果未知，并说明原因。
- **目标打印机：** 任务首次发送时记录目标打印机。重试和未知核对都发往同一台，不改投。
- **档口路由：** `printRoutes` 把「厨房」和「前台」各自指向一台打印机。没有配置的档口继续用模拟打印。测试页可以指定打印机。
- **厨房送达记录同步：**

  | 打印结果 | 送达记录 |
  | --- | --- |
  | 已发送 | 已送达，来源为 printer |
  | 失败 | 失败 |
  | 结果未知 | 结果未知，阻止结账 |

**人工核对（`resolveUnknown`）：** 必须填写说明，并记录核对人。
- **已出纸：** 任务记为已打印（人工确认）。
- **未出纸：** 原任务作废，生成**关联原任务的补打**。原送达记录标为已被接替，不再阻止结账，后续由补打任务的记录追踪。

## 界面

**系统管理 → 终端与打印：**
- 打印机列表：名称、IP 和端口、58mm（32 列）或 80mm（48 列）、是否查询状态、是否启用。
- 支持新增、编辑、删除、打测试页。
- 档口路由：厨房、前台可以各选一台打印机或模拟打印。
- 保存时校验名称、IP 或主机名、端口、纸宽。有发送中或结果未知任务的打印机不能删除。

**打印队列：**
- **表头：** 显示打印机台数、失败张数、待核对张数，并说明「已发送不等于已出纸」。
- **状态：** 已打印、已发送 · 状态正常、已发送 · 未回状态、发送中、失败（附原因）、结果未知 · 待核对。
- **补打：** 补打任务注明原任务，人工核对的说明显示在内容里。
- **核对：** 结果未知的任务提供「核对」入口，可选「已出纸」或「未出纸 · 补打」。

**词条：** en.json 新增 64 条。

## 验证

**单元测试：** 新增 `EscPosPrintTest` 共 8 项，内置一台假 ESC/POS 网口打印机，可模拟缺纸、发送后报错、写入中断开。全部 130 项通过，打印和 LAN 测试连续多次运行都稳定。
- **编码：** 初始化指令、GB18030 中文、切纸指令。
- **网关打印：** 中文内容正确，厨房送达记录为已送达，来源为 printer；前台未配置路由时不会发往厨房打印机。
- **离线：** 打印机离线时任务失败，退避期内不重试；恢复后只打一张。
- **缺纸：** 发送前查到缺纸，不发送任何打印数据。
- **发送后报错：**
  - 任务记为结果未知，阻止结账，一小时后也不会自动重打。
  - 说明为空时拒绝核对。
  - 确认未出纸后生成关联补打，补打带「补打」标记并打出，结账恢复。
- **写入中断开：** 记为结果未知。
- **重启：** 发送中的任务改为结果未知，不会自动发送。
- **校验与测试页：** 打印机配置校验生效，80mm 测试页正常。

**模拟器（pos_tablet 作主 POS，假打印机跑在本机 9100 端口，经 10.0.2.2 访问）：**
- 添加打印机后打测试页，收到的中文、纸宽、地址、时间都正确。
- 厨房路由到这台打印机后，A06 送厨打出厨房单「酸梅汤 ×2」，状态为「已发送 · 状态正常」。
- 让打印机报告缺纸后送厨：没有出纸，任务记为「打印机缺纸」，页头显示厨房 1 张待处理。换纸后自动重试，只打一张。
- 让打印机在发送后报错：任务记为「结果未知 · 待核对」，没有自动重打。核对选择「未出纸 · 补打」后，原任务记下核对人和说明，补打注明原任务并带「** 补打 **」打出，厨房待处理提示消失。
- 全程没有崩溃。

## 仍未覆盖

- **真机核对：** 必须用一台真实网口小票机确认以下几点：
  - 中文模式：部分型号不需要 `FS &`，或者默认编码不是 GB18030。
  - 切刀指令：是否支持 `GS V B`。
  - 状态字节：位定义是否一致；不回状态的型号要关闭状态查询。
- **其他连接方式：** USB、蓝牙、厂商云打印都没有接入。
- **其他打印内容：** 没有图片和 Logo 位图打印，也没有二维码指令。
- **多目标：** 一个档口只路由到一台主打印机，还不支持同时打到多台（副本）。已完成的有：按菜品分档口拆单（见下文）；备用打印机与手动改投（见[厨房送达目标与多设备方案](厨房送达目标与多设备方案-2026-11-11.md)「B 备用打印机实施记录」）。
- **打印机发现：** 不会自动发现打印机，需要手动填写 IP。
- **出纸确认：** 「已发送」不是出纸确认，网口 ESC/POS 本身无法证明纸真的打出来了。

## 厨房单按档口拆分（2026-11-11 补充）

**拆单**
- 送厨时，厨房单和厨房屏任务卡用同一套档口规则：按菜品分类找到档口，没有映射的归默认档口。
- 每个档口一张单。
  - 只涉及一个档口时，任务号仍是 `P-批次`，兼容旧数据。
  - 涉及多个档口时，任务号是 `P-批次@档口`，和厨房屏卡号一一对应。
- 门店配置了多个档口时，单头写成「【厨房单·档口】桌号」，任务标题也带档口名。
- 退菜单打到被退菜品所在档口的打印机。

**路由**
- 每张厨房类任务记录所属档口（`PrintJob.station`）。路由按以下顺序查找打印机：
  1. 本档口的打印机。
  2. 默认档口的打印机。
  3. 旧的「厨房」路由。
  4. 都没有时，用模拟打印。
- 前台类单据仍走前台路由，不受影响。
- 「终端与打印 → 档口路由」逐个列出厨房档口：
  - 默认档口可以选择「模拟」或某台打印机。
  - 其他档口可以选择「同默认」或某台打印机。
- 送达记录的目标显示为「某档口打印机」。每张单各自记录送达状态，失败、核对和补打互不影响；补打保留原档口。
- 升级恢复时，只要某批次已有任何档口的厨房单，就不会再补出这个批次。

**验证**
- **单元测试：** 新增 1 项，用两台假打印机覆盖以下场景：
  - 热菜单只打到热菜机，吧台单只打到吧台机。
  - 打印单号与厨房屏卡号一致。
  - 两条送达记录的目标分别正确。
  - 退吧台饮品时，退菜单只打到吧台机。
  - 未设置打印机的档口跟随默认档口；默认档口改了打印机，它也跟着改。
  - 前台单不走厨房路由。

  全部 149 项通过。
- **模拟器：**
  - 主机（emulator-5600）新增 BarPrinter（10.0.2.2:9101），Bar 档口路由到它；厨房档口仍是 Kitchen1（9100）。
  - A08 同时送厨麻婆豆腐和酸梅汤。
    - 9100 只打出「【厨房单·厨房】A08 麻婆豆腐 ×1」。
    - 9101 只打出「【厨房单·Bar】A08 酸梅汤 ×1」。
  - 打印队列两条都是「已发送 · 状态正常」，打印机分别为 Kitchen1 和 BarPrinter。
  - 没有崩溃。

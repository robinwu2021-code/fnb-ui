# 厨房送达目标与多设备方案（2026-11-11）

**进度：** A 和 B 的备用打印机已实现（2026-11-11），见文末「A 实施记录」「B 备用打印机实施记录」；B 的多打印机副本和 C 仍是方案。

本文最初是方案稿，A 实现后在文末补充了实施记录。它整理厨房出单剩下的三项工作：

- **A. 必需送达目标：** 纸质厨房单和厨房屏同时存在时，规定哪个必须送达，以及部分失败时怎么处理。
- **B. 多台打印机与备用打印机：** 一个档口同时发到多台打印机；主打印机坏了时改用备用打印机。
- **C. 同档口多块厨房屏：** 一张卡只交给其中一块屏。

三项都建立在已完成的「分档口」基础上：

- 送厨按档口拆卡。
- 厨房单单号与厨房屏卡号一一对应：`P-批次@档口` ↔ `批次@档口`。

## 现状

| 环节 | 现在的行为 |
|---|---|
| 纸质厨房单 | 每档口一张 `PrintJob`，路由到一台打印机。每张单对应一条 `KitchenDelivery`，状态为：待出单 / 已送达 / 失败 / 未知 / 人工确认。 |
| 厨房屏 | 每档口一张 `KdsTicket`。厨房屏落盘后发回执，主机记录 `deliveredAt / deliveredRev`。厨房屏的送达不进入 `KitchenDelivery`。 |
| 结账拦截 | 只看纸单：有 `Failed / Unknown` 且没有被补打接替时，拦住结账（`DeliveryRules.checkoutBlock`）。 |
| 打印目标 | 首次发送时固定 `printerId`。结果未知时不改投其他打印机，避免重复出单。 |
| 多块屏 | 同档口每块屏都拉到同一张卡，状态以主机为准。任意一块屏的回执都算送达。 |

**问题**
- 只用厨房屏的门店：纸单走模拟打印，会被视为已送达，厨房屏没收到也不会拦结账。
- 纸单加厨房屏的门店：两条链路各算各的，没有统一规定什么叫「这张单已送到厨房」。

## A. 必需送达目标

### 规则

每个档口配置一个**出单方式**：

| 出单方式 | 必需目标 | 适合的门店 |
|---|---|---|
| 仅纸单（默认） | 纸单送达 | 没有厨房屏，或厨房屏只作参考。与现在的行为一致，升级后不变。 |
| 仅厨房屏 | 厨房屏送达 | 无纸化厨房；纸单不打，或只作记录。 |
| 纸单或厨房屏 | 任一送达即可 | 两者互为备份，其中一路坏了不影响营业。 |
| 纸单和厨房屏 | 两者都要送达 | 档口靠纸单出品、出菜口靠厨房屏，两路都不能少。 |

「送达」只表示送到了，不等于厨师已接单：

- 纸单：打印机回报已发送，或人工确认已出纸。
- 厨房屏：厨房屏持久落盘后发回执。

### 数据

- `StoreData.stationDelivery: Map<档口, DeliveryMode>`。没有配置的档口按「仅纸单」处理，旧数据不需要迁移。
- `KitchenDelivery` 增加两个字段：
  - `channel`：取值 `paper` 或 `screen`。旧记录默认 `paper`。
  - `ticketId`：已有字段，与厨房屏卡号一致，这里继续沿用。
- 主机创建厨房屏卡时，同时生成一条 `channel=screen` 的送达记录：
  - 收到回执 → 已送达。
  - 超过**等待时限**仍没有任何该档口的屏收到 → 失败（未送达）。时限暂定 60 秒，可配置。
  - 厨房屏不会出现「结果未知」：回执只有收到和没收到两种结果。
- 出单方式变更写入 `KitchenDeliveryPolicySaved` 事件，需要门店设置权限，只影响之后送厨的单。

### 判定与部分失败

按**一张卡**（同一个 `ticketId`）汇总该卡所有渠道的送达记录：

| 出单方式 | 已满足 | 需处理（拦结账） | 只提示（不拦） |
|---|---|---|---|
| 仅纸单 | 纸单已送达 | 纸单失败或未知 | 厨房屏未收到 |
| 仅厨房屏 | 厨房屏已送达 | 厨房屏超时未收到 | 纸单失败 |
| 纸单或厨房屏 | 任一已送达 | 两路都失败、未知或超时 | 其中一路失败 |
| 纸单和厨房屏 | 两路都已送达 | 任一路失败、未知或超时 | — |

- `DeliveryRules.checkoutBlock` 改为按卡判定「需处理」，提示文案说明缺哪一路，例如「A08 热菜：厨房屏未收到」。
- 同步中心的「厨房送达」列表按卡分组，每张卡下面列出各渠道的状态。

**需处理时的操作**
- 纸单失败：自动重试（已有），或手动补打（已有）。
- 纸单结果未知：人工核对（已有）。
- 厨房屏超时：
  - 提示「厨房屏离线」，屏重新上线后会自动补拉，不需要重发。
  - 可以选「改打纸单」：给这张卡补出一张纸单，纸单送达后视为满足。
  - 也可以人工确认已口头通知厨房。
- 人工确认：沿用现有规则，必须填写原因，并记录人员。

### 界面

- 「系统管理 → 厨房档口」：每个档口加一项「出单方式」。
- 出菜看板的档口标签显示汇总状态，例如「Bar · 屏已收 · 纸单失败」。
- 顶栏「同步」图标的待处理数改为按卡计数。

### 测试要点

- 四种出单方式分别覆盖：
  - 单路失败。
  - 两路失败。
  - 未知。
  - 超时。
  - 人工确认后是否还拦结账。
- 「仅厨房屏」时，屏离线超时会拦结账；屏重新上线补拉后自动解除。
- 「改打纸单」满足后解除拦截，并且只打一次。
- 旧数据（没有 `channel` 字段）按纸单处理，结账行为不变。

## B. 一个档口多台打印机与备用打印机

这里其实是两个不同的需求：

- **多目标：** 同一张单同时打到几台打印机，例如档口一张、出菜口一张。
- **备用：** 主打印机坏了时，改由另一台打印机代打。

### 多目标

- 路由从「档口 → 一台打印机」扩展为「档口 → 主打印机 + 若干副本打印机」：
  - `printRoutes` 保持不变，作为主打印机，兼容旧数据。
  - 新增 `printCopies: Map<档口, List<打印机>>`。
- 送厨时，每个目标生成一张独立的 `PrintJob`：
  - 主单号不变，仍是 `P-批次@档口`。
  - 副本为 `P-批次@档口~打印机id`，单头标「副本」。
- 只有主单计入 A 方案的「纸单送达」。副本失败只提示，不拦结账。这样多加一台出菜口打印机，不会让结账更容易被卡住。
- 副本的重试、补打、核对与主单完全独立。

### 备用打印机

- 每个档口可以设置一台备用打印机：`printBackup: Map<档口, 打印机>`。
- **只在「确定没发出」时改投：** 主打印机连续失败 2 次，或首次失败超过 30 秒（两个值可配置），网关把任务改投备用打印机：
  - 重设 `printerId`。
  - 单头加「（备用机代打）」。
  - 写一条日志，记录原打印机和失败原因。
- **结果未知不自动改投：** 维持现有原则，避免同一张单在两台打印机上各出一张。人工核对为「未出纸」后生成的补打，如果主打印机仍不可用，会直接走备用打印机。
- 主打印机恢复后，新单回到主打印机；已改投的单不改回。
- 打印队列里失败的单增加「改投到…」按钮，可以手动选择任意一台已启用的打印机。

### 界面

「终端与打印 → 档口路由」每个档口一行，有三个选项：

- 主打印机：单选。
- 副本打印机：多选。
- 备用打印机：单选，不能与主打印机相同。

### 测试要点

- 主打印机加两台副本：打出 3 张，只有主单影响送达判定。
- 主打印机关机（连接被拒，确定没发出）：重试后改投备用，备用打印机出单并带「备用机代打」，送达判定变为已送达。
- 主打印机在发送中途断开（结果未知）：不改投，进入人工核对；核对为「未出纸」后的补打走备用打印机。
- 删除备用打印机，或把它停用后，路由自动失效，不会发往已停用的打印机。

## C. 同档口多块厨房屏只交给其中一块

### 两种模式（按档口配置）

| 模式 | 行为 | 适合的场景 |
|---|---|---|
| 同步显示（默认，现状） | 每块屏都显示全部卡，任一屏操作，各屏同步 | 一个厨房挂多块屏方便查看 |
| 分派 | 每张卡只属于一块屏，其他屏不显示或显示为灰 | 同档口多名厨师各做各的，例如两口炒锅 |

### 分派方式：先接单者负责（推荐）

- 新卡对该档口所有在线屏可见，状态为「待接单」。
- 某块屏点「接单」时，主机按现有版本仲裁，第一块成功的屏成为**负责屏**：
  - 卡上记录 `owner = 设备ID` 和 `ownerName`。
  - 其他屏晚到的接单请求被拒绝，提示「已由 2 号屏接单」。
- 之后的「制作中 / 完成 / 撤回」只接受负责屏的命令。主机侧用 `RemoteOrigin.deviceId` 校验，这部分基础已经有了。
- 卡被接走后，其他屏把它折叠到「其他屏」分组，默认隐藏，可以展开查看。
- **转交与收回：**
  - 负责屏可以「释放」，卡回到待接单。
  - 店长可以在主机出菜看板上「收回」或「指派给某块屏」，需要权限。
- **离线处理：** 负责屏离线超过 N 分钟（暂定 3 分钟）且卡还没完成时，出菜看板标红「2 号屏离线」，提示收回。不自动收回，以免厨师其实还在做。

这样做能直接复用现有的版本仲裁和命令幂等，改动最小。

**备选：主机自动分派。** 主机在建卡时按在线屏轮流分派，或分给待做最少的屏。厨师不用抢单，但需要主机准确知道每块屏是否在线，以及每块屏还有多少活。屏离线时还要重新分派，复杂度更高，建议放在第二步。

### 送达判定

与 A 方案一致：该档口任意一块屏收到即算送达。分派只决定「谁来做」，不影响「是否送到厨房」。

### 数据与同步

- `KdsTicket` 增加 `owner` 和 `ownerName`，接单时写入，释放或收回时清空，每次变化 `rev + 1`。
- 拉取规则不变，所有卡都下发，由屏本地按 `owner` 分组显示。好处是切换负责屏、收回后不需要重新拉取。
- 新增命令：`KdsReleased`、`KdsReassigned`。它们与接单命令一样走主机仲裁，并且幂等。

### 测试要点

- 两块屏同时接同一张卡：只有一块成功，另一块得到明确提示；各屏最终状态一致。
- 非负责屏发起「完成」被拒绝；负责屏释放后，另一块屏可以接单。
- 负责屏离线：看板提示；店长收回后，另一块屏可以接单。
- 同步显示模式下行为与现在完全相同（回归）。

## 需要确认的问题

1. **默认出单方式：** 建议默认「仅纸单」，保持现有行为。门店配好厨房屏后，是否要主动提示改成「纸单或厨房屏」？
2. **厨房屏等待时限：** 超过多久算没收到？暂定 60 秒。
3. **备用改投的阈值：** 暂定连续失败 2 次或 30 秒。厨房出单希望更快切换吗？
4. **多屏分派：** 先做「先接单者负责」，自动分派以后再做，可以吗？
5. **负责屏离线：** 只提示、由店长收回，还是超过时限自动释放？

## A 实施记录（2026-11-11）

**和方案的差异**
- **厨房屏送达记录只在需要时生成：** 只有出单方式含厨房屏的档口才生成。「仅纸单」档口不生成，避免没有厨房屏的门店出现大量「未收到」。
- **按发出时的方式判定：** 一张卡如果没有厨房屏记录，说明送厨时是「仅纸单」（或者是旧数据），就按「仅纸单」判定。之后改了出单方式，不会改变已发出单据的判定结果。
- **模拟纸单的处理：** 在非「仅纸单」方式下，模拟打印出的纸单（没有真实打印机）不算真实送达。例如「纸单或厨房屏」的档口没有配打印机时，实际只靠厨房屏。
- **没有拦结账的问题也会提示：** 说明栏标「仅提示：」，状态仍为「已满足」。
- **等待时限：** 暂时固定为 60 秒（`DeliveryRules.SCREEN_TIMEOUT_MS`），还不能配置。
- **出菜看板：** 档口标签暂未改为显示汇总状态，仍显示厨房屏的制作状态。

**实现要点**
- **模型：**
  - `DeliveryMode` 有四种取值。
  - `StoreData.stationDelivery` 保存各档口的出单方式。
  - `KitchenDelivery` 新增 `channel / station / covers`。
  - `DeliveryRules.groups()` 按 ticketId 汇总，判定逻辑见方案 A 的表格。
- **送厨：** 出单方式含厨房屏的档口，同时生成 `channel=screen` 的记录，`jobId` 为 `S-卡号`。
- **厨房屏回执：** 把对应记录置为已送达；先超时、后来又收到的，也会自动解除。
- **超时：** 主机每 10 秒检查一次，把超时的记录置为失败，并注明「60 秒内没有某档口厨房屏收到」。已取消的卡不判定。
- **改打纸单（`printForScreen`）：**
  - 只在厨房屏失败、且还没有改打或改打已失败时可用。
  - 用卡上仍有效的菜品出一张纸单，单头注明「厨房屏未收到，改打纸单」。
  - 送达记录带 `covers=screen`，送达后视为厨房屏已满足。
- **人工确认：** 按卡确认所有未送达的渠道，必须填写原因，并记录人员。
- **补打：** 沿用原单的 ticketId，归到同一张卡汇总。旧版被补打接替的记录不再显示为失败。
- **设置：** 「厨房档口」页每个档口可选出单方式，保存时写入 `KitchenDeliveryPolicySaved` 事件（需要门店设置权限）。
- **同步中心：** 「厨房任务」按卡列出出单方式、各渠道状态、汇总状态和说明，可以操作「改打纸单」和「人工确认」。顶栏待处理数按卡计数。

**验证**
- **单元测试：** 新增 7 项，覆盖：
  - 仅纸单兼容旧行为。
  - 仅厨房屏：超时拦结账，迟到回执自动解除。
  - 改打纸单送达后满足，并且不重复改打。
  - 纸单或厨房屏：需要至少一路真实送达，模拟纸单不算。
  - 纸单和厨房屏：纸单未知时仍拦，人工确认后解除。
  - 已取消的卡不拦。
  - 旧版补打数据不拦。

  全部 156 项通过。
- **模拟器：**
  - 主机把「厨房」设为纸单或厨房屏，「Bar」设为仅厨房屏，`KitchenDeliveryPolicySaved` 事件已写入。
  - 关闭 Bar 厨房屏后送厨酸梅汤和麻婆豆腐。60 秒后：
    - 结账被拦，提示「A08 Bar：厨房屏未收到」。
    - 厨房那张卡已由 Kitchen1 打出，状态「已满足 · 仅提示：厨房屏未收到」。
  - 在同步中心点「改打纸单」：BarPrinter 打出「厨房屏未收到，改打纸单 / 【厨房单·Bar】A08 酸梅汤 ×1」，这张卡变为已满足，顶栏待处理数清零。
  - 重新打开 Bar 厨房屏后，它补拉到这张卡，主机显示「屏 已送达」。
  - 两台都没有崩溃。
- **发现并修正：** 旧版被补打接替的失败纸单一度被算作待处理，已修正，并补了测试。

## B 备用打印机实施记录（2026-11-11）

**和方案的差异**
- **适用范围：** 备用打印机不只用于厨房档口。前台（预结单、结账单、交班单）同样可以设置备用打印机。
- **改投阈值：** 确定没发出（连接失败、缺纸、脱机、无响应）达到 2 次，或首次失败已超过 30 秒，就改投。常量在 `KdsRules.FAILOVER_ATTEMPTS / FAILOVER_MS`，暂时还不能配置。按现有的重试退避，主打印机连不上时，大约 4 秒后会第二次失败并改投。
- **主打印机已停用或删除：** 还没发出的单直接走备用打印机，不必等失败。
- **按主路由逐行设置：** 备用打印机只能在已经配了主打印机的路由上设置。没有主打印机的路由本来就是模拟打印，设备用没有意义。

**实现要点**
- **模型：**
  - `StoreData.printBackups` 记录「路由键 → 备用打印机」。
  - `PrintJob` 新增 `failoverFrom`（改投前的原打印机）和 `firstFailAt`。
  - 路由键的查找规则与主路由相同：本档口 → 默认档口 → 旧「厨房」路由。
- **自动改投（`finishPrint`）：**
  - 只在结果为「确定没发出」时改投，每张单只改投一次。
  - 改投后：`printerId` 换成备用打印机，任务回到排队、立即发送。
  - 单头加「备用机代打（原 某打印机 失败原因）」，并写一条日志。
- **结果未知不改投：** 仍走人工核对，避免两台打印机各出一张。
- **手动改投（`redirectPrint`）：**
  - 打印队列里失败的单有「改投」按钮，可以选任意一台已启用的打印机。
  - 单头注明「手动改投」。
  - 结果未知的单必须先核对；已被核对作废的单不能改投。
- **设置：** 「终端与打印 → 档口路由」在每个已配主打印机的路由下多一行「备用」，可选「不设」或另一台打印机（不能和主打印机相同）。删除打印机时，同时清掉指向它的备用设置。
- **队列显示：** 改投过的单，打印机一栏显示「某打印机（改投）」。
- **送达判定：** 改投后的单送达，原厨房单的送达记录随之变为已送达，A 方案的结账拦截自动解除。

**验证**
- **单元测试：** 新增 5 项，覆盖：
  - 主打印机连续两次连不上后改投，备用打印机出单，单头带「备用机代打」和原打印机名；送达后不拦结账，之后不会重复发送。
  - 结果未知时不改投，也不能手动改投。
  - 主打印机已停用时，直接走备用打印机。
  - 手动改投失败的单，单头带「手动改投」。
  - 配置校验：备用不能和主打印机相同，打印机必须存在，删除打印机后清掉备用设置。

# Android POS 下一阶段实施方案

日期：2026-11-10。状态：用户已确认方案，第一批N1-01/N1-04已开始执行，其他任务按阶段推进。

用户已确认[任务顺序](../android/下一阶段任务与执行顺序-2026-11-10.md)：补齐事件 → 完善命令契约 → 拆分确认状态 → 离线授权与主副POS → 打印/KDS/云端及支付联调。本文把该顺序落实为数据、模块、迁移和验收方案。离线授权默认短期7天、长期90天，保留可配置能力。

## 1. 现状、目标与实现选择

现有Android工程位于`bak/pos-android`。已有SQLite v2、本地事务、命令Inbox、原回执、事件待发以及主要营业操作的事件；页面仍使用LocalWorkspace和门店快照。当前`local-page`、`page-order-stream`、聚合占位状态及结果快照都是过渡实现；SyncEngine/PrintEngine仍为模拟服务。

目标是让单机、局域网主副机及联网门店共用同一组业务规则和持久命令边界，逐阶段替换模拟服务。首期保留紧凑页面及共享组件，不重做视觉方案。

| 实现路线 | 取舍 | 本方案 |
| --- | --- | --- |
| 继续扩充快照与事件，按操作自由拼装字段 | 改动少，但难以约束遗漏、重试和跨机一致性 | 只作为当前兼容输入，不作为最终通信契约 |
| 事务数据库保存权威业务状态，类型化命令处理器同时产生事件及任务 | 可渐进迁移，明确业务与副作用边界 | 推荐，沿用既有主POS协调方向 |
| 全量事件溯源，所有业务从日志重建 | 要求完整历史、事件演进和重放规则，当前历史不满足 | 首版不采用 |

此处新增的模块名、分层和迁移方式是实施建议；用户已确认执行顺序，不代表全部细节已批准。

## 2. 核心边界

- 当前主POS的事务数据库是门店活动业务的权威；事件是同事务产出的分发和追溯记录，不是另一份可独立修改的权威。
- 页面发出业务意图，处理器读取当前数据并校验，不接受副POS上传整张订单覆盖主机。
- 业务状态、幂等回执、事件、账本和待执行任务同事务提交；持久成功后才通知页面。外部支付、出纸及网络请求均在事务外执行。
- 副POS保存原命令再发送。重试复用原ID；收不到结果显示待确认，不自动生成第二笔业务。
- 网络可达、设备身份有效、员工有权限、订单可修改是四类检查；不能用一个online字段代替。
- 模拟模式显式隔离；模拟确认不能升级为真实云端、厨房或支付凭证。

## 3. N1：写入覆盖与类型化事件

先建立Repository写入口覆盖表，状态包括“已有事件、待接入、仅本机、需独立设备日志”。避免将所有修改机械套进当前依赖tableId的事件构造函数。

| 写操作组 | 事件或记录建议 | 需保存的业务信息 |
| --- | --- | --- |
| 清台开始/完成、清空新菜、备注、催菜/上菜 | TableCleaningStarted/Finished、DraftCleared、NoteChanged、KitchenProgressChanged | 桌台/订单身份、行身份、前后状态、操作者；状态名称与实际动作对应 |
| 会员及优惠变更 | MemberLinked/Unlinked、BenefitsChanged | 会员引用、规则版本及本单计算快照，不记录凭据；真实资产能力仍未放开 |
| 预订新建/取消/到店 | ReservationCreated/Cancelled/Arrived | 稳定预订ID、关联桌台及营业周期；到店开台同事务产生关联事件，不能只记录TableOpened |
| 区域、分类、规格、商品、餐牌与门店配置 | 对应实体Created/Updated/Published/Disabled | 稳定ID、实体版本、变更内容、配置生效范围；删除使用墓碑 |
| 库存调整 | StockAdjusted + 库存流水 | 商品/SKU、调整前后数量、差量、原因及人员；不可只覆盖余额 |
| 交班 | ShiftClosed + 固化交班记录 | 班次ID、账本范围、实盘/应收/差额、未决项及打印任务引用 |
| 预结单、补打、打印/KDS执行反馈 | 设备任务日志及业务关联事件 | 原任务、执行尝试、设备、结果证据；未知状态不可改成确定失败后自动重派 |
| 模拟syncNow/process | 模拟任务日志 | 显式simulation来源；真实服务接入时不能复用其成功标记 |
| 登录/注销、选店/选桌、字体/语言/布局 | 本地会话/偏好；安全操作另记受限审计 | 不进入营业同步事件；不上传账号密码、哈希或密钥 |
| 演示数据重置 | 仅演示环境管理记录 | 真实营业构建禁止无痕清库；不通过重置回退命令序号或清除未确认资金记录 |

### 事件构造

提取独立`BusinessEventFactory`与类型化`ChangeSet`，LocalWorkspace只负责调用规则和事务。ChangeSet按实体列出upsert、删除墓碑及关联ID，支持一条命令影响多张桌、多个事件和多个任务；不再假设每条事件都有tableId。

营业事件必须具备类型和payloadVersion；支付、审计、预订、库存和交班分别使用专属载荷。保留现有多桌、挂单增删、打印/Outbox增量字段的兼容解码，不把旧事件静默改写成新事实。

N1仍沿用现有页面命令流；它补足覆盖及载荷，不提前承诺订单级网络并发控制。

**阶段完成标准：**每个写入口有明确归类；拒绝和无变化操作不产生虚假营业事件；业务与事件同事务；跨桌、到店开台、库存和交班有失败回滚测试。新页面文案和状态复用现有中英文组件。

## 4. N2：命令协议、聚合、发送端与迁移

### 4.1 命令与事件信封

| 内容 | 字段/约束 |
| --- | --- |
| 协议 | schemaVersion、payloadVersion、type；未知版本拒绝或进入隔离队列 |
| 作用域 | tenantId、storeId、deviceId、actorId；所有ID由可信上下文校验，字符串不是身份证明 |
| 幂等 | commandId及规范化请求摘要；相同ID不同内容拒绝，重试返回原持久回执 |
| 关联 | eventId、causationId=commandId、correlationId；多事件保存完整结果列表 |
| 并发 | coordinatorId、authorityEpoch、参与聚合的expectedRevision集合 |
| 授权 | authorizationRef、policyVersion；验证通过后才进入业务处理器 |
| 时间与顺序 | 客户端发生时间仅供展示；主机接受时间、门店日志序号及epoch用于追踪 |

命令载荷为业务意图，例如商品/SKU/数量、源目标订单ID、选中行和支付意图ID。价格、权限、库存和可用优惠由协调节点重验；不能信任客户端提交的最终订单快照。

回执区分Committed、Rejected、Conflict。Committed包含参与聚合的新版本及事件编号；Rejected/Conflict作为终态结果持久保存，重复同ID返回同结果。暂时不可用或未验证身份的请求不伪造业务成功；允许在凭据恢复后重试原请求。客户端不可通过刷新时间戳或授权字段改变已保存命令的摘要；传输凭据单独更新，需改变业务内容时创建新命令并关联旧请求。

### 4.2 聚合与权威读模型

建议实体：Order、TableSession、Reservation、Catalog/StoreConfig、StockLedger、Shift、DeviceTask。每次营业生成稳定orderId和tableSessionId；桌号仅为位置显示。换桌保留订单ID并变更桌台会话；并台保留来源关联；拆单生成目标订单或关联已有订单，保留行来源。

跨桌操作在同一门店事务内校验所有参与对象的版本，任一冲突整笔拒绝，不逐桌提交。门店日志序号用于增量读取，不能替代订单版本。

初期保留每店单写协调服务，逐实体迁移权威状态；页面现有StoreData作为查询投影。每项领域操作切换时同时停止其旧快照写入口，禁止新聚合和旧LocalWorkspace分别修改同一事实。未迁移操作仍走兼容事务适配器；明确列出归属，不允许绕过版本维护。全部相关写入口迁完前，不开放跨POS写入。

金额专项在新协议字段冻结前推进：统一整数Long分、币种、数量/金额上限与舍入规则，迁移旧Int值，校验乘法/累加溢出；新支付和库存账本不可继续依赖未定义的浮点规则。

### 4.3 持久发送与Inbox

新增独立`CommandOutbox`，区别于现有厨房/支付演示Outbox和事件待发队列。记录原请求、摘要、创建作用域、目标主机、尝试、下次重试、最后错误及回执。

状态建议：Saved → Waiting/Sending → Committed / Rejected / Conflict；发送超时回到Waiting，保持结果待确认。进程重启先查询回执或重投同ID。切店不更改已保存请求的storeId；页面离开不取消已提交业务，只停止观察。

不支持命令事务的SnapshotStore必须明确拒绝，内存测试适配器显式实现测试能力，去掉当前默认静默仅存快照的生产风险。幂等记录保留覆盖重试与最长离线窗口加恢复裕量；具体保留期随存储容量及服务策略确定。清理不得使已完成资金请求重新执行；超过窗口的旧请求进入过期/查询处理，不能当作全新请求。

### 4.4 数据迁移与恢复

SQLite数据库版本和业务信封版本分别管理。每次升级先校验旧库及恢复条件，在事务内迁移，保留迁移记录；失败不清库、不自动降为演示数据。备份需覆盖全部业务、Inbox/Outbox、事件游标及版本，同一恢复点导出；设备私钥另按身份恢复流程处理。

旧快照导入为带来源的基线；已有事件保留原ID、顺序、载荷及legacy版本。原`local-page`不是可信设备身份，不冒充新设备签名；旧记录通过受控历史导入通道核对，不按新命令重新执行出纸或收款。保留旧流到新流的明确水位和映射；不能将旧序号清零后混入同一同步流。

历史没有orderId的已结账记录保留关联未知标记，不凭桌号推断是哪一次营业。当前活动订单分配新ID并保存迁移映射。损坏库提供只读诊断、导出、备份恢复及管理员确认页面；无完整备份时明确缺口。

**阶段完成标准：**重复/并发/超时/重启/切店命令可验证；存储中途失败不产生半笔状态；旧数据升级不丢任务及账本；没有真实身份/权限的远端命令不能进入业务写入口。

## 5. N3：确认状态、结账策略与界面

| 状态轴 | 记录对象 | 页面表达 |
| --- | --- | --- |
| localCommit | 当前设备请求 | 已保存/保存失败 |
| storeCommit | 主POS回执 | 待主机确认/已接受/冲突/拒绝 |
| kitchenDelivery | 每个必需目标及尝试 | 待发/已持久接收/失败/未知/人工核对；厨师制作进度另列 |
| cloudSync | 业务事件 | 待上传/云端已提交/冲突/待人工处理 |
| paymentState | 支付意图及账本 | 未支付/处理中/未知/成功/失败/退款中等 |

这些状态分别持久保存，通过业务ID关联；厨房和云端拥有不同ACK，不让一个队列完成顺带把另一状态改成功。旧Queued/Sent、Printed/synced迁移时记录legacy/simulation来源，无真实回执则显示历史待核实。

建议结账规则：满足主POS提交及必需厨房交付条件后，可在云待同步时本地现金记账；线上支付必须取得渠道可信结果。**这是待确认的经营策略，实施状态拆分时先维持现有new/queued阻止结账。**每档口打印/KDS/双目标及人工交付权限要单独配置；任一必需目标失败或未知时必须处理，不能自动忽略。

同步中心分为本机命令、主机回执、厨房任务、云事件和异常处理；页头使用紧凑入口显示各端点连接及待处理数。显示最近成功时间、失败原因及业务定位；确认未知结果、人工补打或人工交付记录人员和原因。网络图标变化不能清队列。

**阶段完成标准：**断云可继续正确显示局域网/厨房状态；部分档口失败可定位；未知支付只提供查单，不引导重复支付；中英文及紧凑布局一致。

## 6. N4–N10：离线身份、通信、设备与云端

| 阶段 | 设计与交付 | 进入下一步的条件 |
| --- | --- | --- |
| N4 身份/离线授权 | 注册或激活时绑定设备公钥、签发OfflineGrant；员工本地认证与设备身份分开；7/90天默认期限、角色/限额、续期及异常时间处理 | 测试签发与生产信任根隔离；到期不删账本；会话不延长父授权；离线不能保证即时收到撤销 |
| N5 主副POS | 发现/手动连接→一次性配对→认证加密→命令/回执→快照水位及增量；主机继续唯一协调 | 至少一主两副验证并发、断网、丢回执、重启；失联副机默认只读/草稿，云可达不自行升主 |
| N6 打印 | 一个明确网关拥有打印机；档口路由生成稳定任务；发送与物理确认分级 | 先完成一种真实型号；未知结果人工核对，补打新尝试关联原任务；不承诺传统设备恰好出纸一次 |
| N7 KDS | 工位配对、持久Inbox、任务修订、制作反馈、恢复游标 | 先持久接收再ACK；厨师接单/制作/完成独立；重复不新增任务、迟到反馈不恢复已取消项 |
| N8 云同步 | 认证端点、事件幂等接收、配置版本、逐流游标、快照+增量、重试与对账 | 远端持久提交才ACK；配置不追溯改历史价格；云端历史导入不触发本地打印或支付 |
| N9 恢复/接管 | 同步恢复点、旧主隔离、授权提升epoch、设备任务所有权迁移及差异对账 | 无法排除旧主继续写入时停止共享写；无仲裁/副本不承诺自动无损切主 |
| N10 资产/支付 | 权威报价、券/储值、库存配额、支付及退款查询、补偿账本 | 真实渠道结果明确；全局资产默认在线校验，离线必须另有互不重叠的额度授权 |

完全无网、无预签凭据的首次注册只建立待认领资料，不假装云注册成功。长期凭证不是永久登录或失联写入权；复制凭证不能复制设备私钥身份。

本节沿用[协同方案](多POS离线局域网与云端协同方案.md)和[同步契约](同步节点与事件契约.md)的安全及设备边界；详细实现随接口、型号明确后形成对应阶段计划。

## 7. 建议模块与文件职责

在现有`core/data`旁渐进提取，名称为建议，不要求一次重构所有页面。

| 模块 | 职责 |
| --- | --- |
| core/model/command | 类型化意图、信封、回执、版本及领域ID |
| core/model/event | 事件载荷、ChangeSet及兼容解码 |
| core/data/command | 处理器、Inbox、持久命令Outbox及事务协调 |
| core/data/storage | SQLite迁移、实体/读模型、账本、备份恢复 |
| core/sync | 连接状态、增量/快照、ACK验证、重试与对账 |
| core/device | 打印/KDS网关接口、任务/尝试、路由与反馈 |
| core/auth | 设备身份、授权校验、本地员工认证、续期及恢复 |
| feature/sync、print、manage、auth | 共享组件下的状态展示和有权限的操作入口 |

规则和处理器不依赖Compose；页面仅观察Repository状态并提交命令。生产适配器和模拟适配器显式区分，不通过网络连通后直接模拟成功。

## 8. 验证与交付

每阶段提交可审阅的代码差异、数据库迁移、必要英文词条、测试结果及文档状态。沿用当前70项单元/12项SQLite设备测试作为历史基线，新增测试按行为补充，不以总数量替代验收。

关键场景：事务每个写入点失败、同ID异内容、双终端同单、切店与后台恢复、丢ACK及重放、版本升级、旧库损坏、授权到期与时钟回拨、部分厨房失败、未知打印/支付、旧主恢复。设备型号和服务未就绪时明确注明仅模拟验收，不标记真实接入完成。

实施批次：**N1覆盖表/构造器 → 订单桌台事件 → 配置库存交班事件 → N2协议/金额/聚合迁移 → 命令发送及恢复 → N3状态与界面 → N4起逐项联调。**每个批次达成验收条件再扩大范围；当前任务是方案评审，不运行代码迁移。

## 9. 待确认经营项与默认保护

尚待确认：厨房交付和现金放行条件、人工交付权限、授权到期宽限、失联副POS临时单、离线资产额度、硬件型号和备用主机、后端与支付联调环境。

未确认时沿用现有经营限制，无自动宽限、无失联副机共享写入、无离线全局资产核销；上述待定项不阻塞N1/N2及N3状态建模。具体设备连接和服务签发不能在缺少真实依赖时宣称完成。

评审记录：独立工程审阅未发现阻碍拆分实施计划的重要问题；本地文档链接及差异格式检查通过。本轮只更新方案与入口文档，未修改业务代码、执行数据库迁移或重新运行应用测试。

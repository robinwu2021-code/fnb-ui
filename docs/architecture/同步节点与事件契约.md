# POS 同步节点与事件契约

日期：2026-11-10。状态：架构草案，尚未实现。配合[多 POS 离线、局域网与云端协同方案](多POS离线局域网与云端协同方案.md)阅读。离线授权默认期限已由用户确认为短期7天、长期90天，保留可配置能力；其他协议字段、会话期限和确认条件仍为建议。

## 1. 节点职责与连接状态

| 节点 | 本地保存 | 接收或发送的内容 | 权威边界 |
| --- | --- | --- | --- |
| 副 POS | 缓存、草稿、命令 Outbox、确认结果 | 向主 POS 提交业务命令；拉取门店事件 | 不独立修改共享订单和桌台 |
| 主 POS / StoreCoordinator | 业务数据库、事件日志、Inbox、Outbox、路由任务 | 仲裁门店命令，分发厨房任务，与云端同步 | 当前门店活动订单、桌台及本地业务的唯一写入协调者 |
| 打印网关 | 打印任务、尝试记录、设备结果 | 接收带唯一编号的厨房或小票任务，返回送达结果 | 仅操作分配给自己的打印机 |
| 厨房屏 KDS | 本工位任务、游标、反馈 Outbox | 持久接收任务，回传接单、制作、完成 | 不自行改价、退款或结算 |
| 云端 | 身份、授权、配置版本、门店事件副本、对账结果 | 签发授权，下发配置，接收事件和核对数据 | 跨门店身份及全局资产；门店营业命令仍由当前主 POS 接受 |

分别检测局域网、主 POS、云端、打印网关及 KDS 的实际可达性。Android 声明有网络不等于这些端点可用；连通性也不等于授权仍有效。状态显示最近成功时间、待处理数量和明确原因。

## 2. 同步触发节点

| 触发点 | 动作及顺序 | 完成条件 / 失败处理 |
| --- | --- | --- |
| 首次在线注册 | 注册主体及门店 → 绑定设备公钥 → 签发授权 → 下载基础快照 | 授权和快照持久化后才显示“可离线使用” |
| 导入离线激活包 | 校验签名、设备绑定、门店、期限和授权版本 → 保存授权及配置 | 无有效激活凭据的首次离线注册仅为待认领；不伪装为云端注册完成 |
| 离线登录 | 验证本地员工凭据、设备授权和权限范围 | 会话期限不能超过父授权；过期进入只读或既定应急策略 |
| 副 POS 配对 | 验证主机身份和设备凭据 → 分配角色 → 拉取快照及游标 | 配对码只用于引导；后续请求仍需设备身份验证 |
| 启动或选择门店 | 校验身份、epoch、数据库版本 → 恢复未确认队列 → 快照及增量握手 | 保留未确认命令；不能用新快照覆盖本机未上传事件 |
| 分类、商品、SKU、餐牌变更 | 云端或管理端产生配置版本 → 主 POS 校验并提交 → 门店广播 | 已点餐行保留当时的名称、价格、规格快照；不追溯改价 |
| 开台、加减菜、折扣、并台 | 副 POS 保存命令 → 主 POS 校验权限及期望版本 → 事务提交 → 返回版本 | 超时为“结果待确认”，用原命令 ID 查询或重试 |
| 送厨 | 主 POS 同一事务记录送厨事件和各工位任务 → 分发 | 每个必需目标分别确认；部分失败不能显示全部送达 |
| 打印或 KDS 反馈 | 设备保存结果 → 回传主 POS → 主 POS 提交事件 → 广播 | 重复反馈不重复推进业务；无法确认的物理打印进入人工核对 |
| 现金结账 | 主 POS 校验订单版本、金额、权限和所需厨房状态 → 保存支付及账本 | 本地正式完成与云端待同步分别显示；现金支付 ID 唯一 |
| 在线支付 | 创建支付意图 → 调用支付方 → 查询或接收可信结果 → 保存支付 | 结果未知先查询，不重新收款；离线不能声称第三方支付成功 |
| 退单、退款、优惠、储值 | 校验权限及资产可用范围 → 主 POS 记录审计、账本和补偿事件 | 全局券和储值默认需在线；离线仅允许已明确预分配的额度 |
| 库存变化 | 主 POS 接受销售或调整 → 记录库存流水 → 广播 → 上传 | 不跨断网节点共享同一可用额度；超额情况单独对账 |
| 交班 | 汇总本地账本、未知支付及待同步项 → 固化交班快照 → 上传 | 是否允许带未决项交班须配置；快照不得被后续同步静默重写 |
| 网络恢复 | 身份及主机握手 → 上传缺失事件 → 下载配置和增量 → 对账 | 按对象和游标恢复；网络图标变绿不能直接清空队列 |
| 主机重启 | 恢复事务日志、Inbox/Outbox、设备任务 → 对比从节点游标 | 恢复后继续使用原事件及任务 ID |
| 主机切换 | 隔离旧主机 → 确认恢复点和缺口 → 分配更高 epoch → 重新握手 | 无法排除双主或确认数据缺口时停止共享写入，保留草稿 |
| 授权过期、撤销或时钟异常 | 阻止新增越权业务 → 保留待同步账本 → 进入恢复流程 | 禁止清除队列或改写历史以绕过授权 |

## 3. 事务、事件与确认

业务状态变更、事件记录和 Outbox 入队必须处于同一数据库事务。主 POS 只有在事务持久提交后才返回 `storeCommitted`。接收端的 Inbox 去重记录、业务更新和回执也要原子提交。

建议以事务数据库承载业务日志；DataStore 继续保存显示偏好。不能依靠多个异步 JSON 快照写入提供上述保证。

| 确认层 | 表达的事实 | 不代表 |
| --- | --- | --- |
| localCommitted | 当前设备已持久保存草稿或命令 | 主 POS 已接受 |
| storeCommitted | 当前主 POS 已提交业务，返回权威版本 | 厨房已收到、云端已收到 |
| kitchenDelivered | 指定网关或 KDS 已持久接收任务 | 已出纸、厨师已接单、餐品已完成 |
| kitchenProgress | 工位接单、制作、完成等明确反馈 | 已结账 |
| cloudCommitted | 云端已持久保存并返回确认游标 | 打印成功或支付成功 |
| paymentState | 未支付、处理中、结果未知、成功、退款等 | 其他各层已完成 |

打印另有 `sentUnverified / confirmed / failed / unknown`；只有设备协议能提供相应证据时才能显示确认出纸。KDS 的制作进度独立于传输确认。

## 4. 建议契约

以下是逻辑字段，尚未固定 HTTP、WebSocket 或本地服务接口。

```json
{
  "schemaVersion": 1,
  "commandId": "device-generated-unique-id",
  "tenantId": "tenant-1",
  "storeId": "store-1",
  "deviceId": "pos-2",
  "actorId": "employee-7",
  "coordinatorEpoch": 12,
  "authorizationRef": "offline-grant-id",
  "aggregateType": "Order",
  "aggregateId": "order-unique-id",
  "expectedRevision": 8,
  "type": "AddOrderItems",
  "correlationId": "operation-unique-id",
  "occurredAt": "2026-11-10T08:00:00Z",
  "payload": {}
}
```

主 POS 接受后生成 `eventId`、`causationId=commandId`、`aggregateRevision`、主机日志位置 `storeSequence`、主机 epoch、接受时间及所用规则版本。金额使用币种和最小货币单位；商品行保存价格、规格、加料及优惠计算结果快照。任务再携带工位、路由版本和原事件编号。

- 幂等范围为 `storeId + deviceId + commandId`，并保存请求摘要和原结果。同编号不同内容拒绝；重复相同请求返回原结果。
- 事件去重使用 `eventId`；厨房任务使用稳定逻辑任务 ID；每次人工补打使用新的尝试 ID，并关联原任务。
- 订单以聚合版本做并发检查；门店序号只表示当前协调日志内的顺序，跨主机 epoch 的承接关系必须记录。设备时间不能作为唯一排序或冲突裁决依据。
- `expectedRevision` 冲突时返回当前版本和具体差异。可安全合并的独立加菜需重新校验后产生新命令；结账、退款、并台等不自动覆盖。
- 传输必须验证设备身份和授权范围；消息中的 `deviceId` 字符串本身不能证明身份。

应用层要明确幂等语义后才能安全重试非幂等业务请求；不能把 HTTP 重试当成业务去重。[HTTP 语义 RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 5. 重连、快照与游标

1. 握手交换身份、协议版本、授权状态、当前主机 epoch、快照版本和已提交游标。
2. 接收方返回缺失范围；发送方按依赖顺序重放原 ID，保存确认后才推进发送游标。因果依赖未到达的事件先等待或请求补齐。
3. 首次初始化使用水位 `W` 的一致快照，再衔接 `W` 之后的事件。先建立可续传的日志读取位置，避免下载快照期间漏掉实时更新。
4. 收到数据并提交本地事务后才推进接收游标；下载完成不等于应用完成。订阅断开后从已提交游标继续。
5. 上传门店事件后再应用云端命令或配置，并不意味着全局严格串行；每个业务依赖仍需校验。云端导入的历史事件不能再次触发打印、收款或送厨。
6. 完成订单、支付、库存流水和任务数量的对账，展示缺失、重复、拒绝及待人工处理项。

指数退避和抖动用于暂时网络错误；鉴权失败、版本不兼容、金额冲突等进入明确处理队列，禁止无限重试。日志保留覆盖最长离线窗口及恢复裕量；超过增量保留范围的节点重新取快照，但先保存并处理自身未确认数据。删除使用带版本的墓碑；只有满足保留策略和必要节点恢复条件后才能清理。

主机云端副本、局域网备份及每个节点的确认进度分别记录。切主时明确最后恢复序号、未复制区间和可能丢失的已确认业务；只有事前采用足够的持久副本确认策略，才能承诺对应故障范围内的数据不丢失。

## 6. 冲突与异常策略

| 对象 / 异常 | 处理策略 |
| --- | --- |
| 同桌多机操作 | 主 POS 顺序提交，版本冲突提示刷新；禁止整单最后写入覆盖 |
| 商品及价格更新 | 配置版本化；进行中订单维持已确认快照，变价必须有显式操作 |
| 并发结账或退款 | 唯一业务 ID、订单版本和账本约束共同阻止重复；未知结果先查询 |
| 跨门店券、储值或库存 | 默认在线核验；离线使用互不重叠的预分配权益和额度，恢复后核销对账 |
| 打印超时 | 查询协议支持的任务结果；结果未知人工确认，不能自动切备机重复出纸 |
| KDS 重复投递或撤回 | 相同 ID 去重，更高修订更新；撤回不等于厨师已停止制作 |
| 旧主机恢复 | 先校验 epoch 并停止旧写入；导出分叉事件人工对账，不能整库覆盖新主 |
| 设备授权过期但有历史待上传 | 保留账本；通过受限恢复通道或管理员续权上传，云端核验授权链和接收证据 |
| 撤销后收到延迟事件 | 隔离待审，不直接丢弃；云端按授权政策和证据认定业务有效性，不能只相信本机时间 |
| 重新安装、磁盘损坏 | 从授权绑定及备份恢复；设备私钥丢失需重新登记，不能仅复制 token 继承设备身份 |

离线期间无法保证立即获知撤销，也无法完全证明设备离线事件的真实发生时间。主机签收和可信时间锚能增强证据，但不能消除该限制；长期授权的风险窗口应与业务权限及额度一起审批。

## 7. 当前工程迁移

当前 `LocalWorkspace` 已将单设备业务快照、现有 Outbox 和打印任务接入 SQLite 事务，保存后才发布内存状态；保留门店级 JSON，尚未实现领域事件日志及 Inbox。`SyncEngine` 和 `PrintEngine` 仍含模拟行为，不能直接扩展为生产主副 POS 协议。见[本地事务存储实施记录](../android/本地事务存储实施记录-2026-11-10.md)。

建议按以下顺序推进：

1. 事务存储、稳定 ID、账本、Outbox/Inbox、版本及恢复测试。
2. 拆分网络、厨房、云端及支付状态；保留旧状态来源。旧 `Queued/Sent` 记录没有真实设备回执时标为“历史状态待核实”，不能迁移成真实送达。
3. 单主 POS 与一个副 POS 的认证、配对、增量和冲突处理。
4. 打印网关与 KDS 的持久接收、反馈、人工补打及设备管理。
5. 云端事件接收与配置下发、离线授权及资产额度。
6. 备份恢复和受控主机切换，再评估自动切换及更多门店规模。

## 8. 验收场景

- 在本地提交、主机提交、设备接收、云端提交及确认返回的每个边界断网或杀进程；恢复后不丢账、不重复扣款。
- 同桌并发加菜、并台和结账，所有节点最终版本一致；冲突有可操作提示。
- LAN 通但云断、云通但主机不可达、仅部分厨房设备不可达，分别显示并执行正确策略。
- 网关断电、未知打印、KDS 重投、部分工位失败，厨房队列不被云端重放再次触发。
- 旧主机恢复、日志缺口、备份落后及分区双主风险出现时，不偷偷合并或继续共享写入。
- 授权到期、复制 token、修改设备时间、离线重启、延迟撤销及重新安装，验证降级与恢复流程。
- 长期离线后的全量恢复、墓碑、旧版迁移和金额对账，确认保留未同步历史及审计证据。

这些是后续实现的验收要求，本次文档整理未执行相关集成测试。

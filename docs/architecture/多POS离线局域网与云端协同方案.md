# 多 POS 离线 局域网与云端协同方案

日期：2026-11-10。状态：架构草案，待业务与设备选型评审。本轮只整理方案，不声明打印机、厨房屏、多机通信或token服务已实现。Android已推进单机持久化基础：SQLite事务保存门店快照及独立队列行、落盘后发布状态、旧DataStore数据迁移；仍为单机业务快照、模拟打印与模拟同步。详见[实施记录](../android/本地事务存储实施记录-2026-11-10.md)。

目标：一家门店支持一个主POS、多个副POS、打印机与厨房屏；分别在完全离线、门店局域网和云端可达条件下持续工作，注册/激活后可在授权期限内离线登录，联网后有序补齐业务数据。

## 1 总体取舍

| 方案 | 优点 | 约束 | 本方案建议 |
| --- | --- | --- | --- |
| 所有POS各自写本地数据，事后互相合并 | 单机独立性高 | 桌台、库存、收款、退菜难以安全合并，容易双收/重复出单 | 不作为共享门店订单的默认方案 |
| 门店主POS作为协调节点，副POS发送命令，主POS再对云同步 | 局域网内无公网也可共享账单、厨房与打印 | 主POS需稳定运行；故障接管必须明确 | 首期采用 |
| 独立门店网关/小服务器协调，POS都是客户端 | 可独立维护和备份，降低收银设备生命周期影响 | 增加硬件、部署与运维 | 协调服务设计成可迁移，后续可部署到网关 |

关键原则：网络恢复不自动改变写入权；云端可达不等于副POS可以绕过主POS改同一张订单。云端是全局身份、配置与归档的权威，门店营业命令由当前门店协调节点串行确认。云端后台对进行中订单的操作也需路由到该节点。

```text
                 云端身份/授权/配置/订单归档/支付服务
                              ↕
                  主POS / 门店协调服务
                  ├─ 副POS A、B、C
                  ├─ 厨房屏：热菜、凉菜、饮品等档口
                  ├─ 打印网关：USB / 蓝牙 / TCP网络打印机
                  └─ 只读备份节点（后续）
```

首期不做各POS对等多主写入，不用整个StoreData JSON覆盖其他终端。现有DataStore偏好可保留；订单、事件、幂等记录、队列和游标建议迁入支持本地事务的数据库，按实体和事件持久化。

## 2 网络环境与营业能力

网络状态至少拆为：`lanReachable`、`coordinatorReachable`、`cloudReachable`、`printerReachable`、`kdsReachable`，另有授权有效性。Android检测到网络能力不能代替对这些服务的实际探测。

| 模式 | 条件 | 主POS | 副POS | 打印/KDS | 云端 |
| --- | --- | --- | --- | --- | --- |
| A 单机完全离线 | 无云、无可用局域网 | 在本机授权范围内经营自己的订单 | 无法访问共享订单；可保存本机草稿 | 本机连接的USB/已配对蓝牙设备可用；远端厨房设备不可用 | 待上传 |
| B 局域网营业 | 可访问主POS，无云 | 协调共享桌台、订单、库存配额与任务 | 经主POS开台、加菜、送厨、现金结账 | LAN档口及网关工作，不依赖公网 | 主POS积累Outbox |
| C 局域网加云 | 主POS与云均可达 | 仍协调门店命令并同步云端 | 经主POS正常工作 | 门店本地执行，云端不重复派发 | 拉配置、传业务、查支付、更新授权 |
| D 仅云可达 | 副POS能上网但连接不到主POS | 若主POS在线，可由受控云通道路由命令到主POS | 不直接创建第二个权威；主POS不可达时降级 | 仅使用可确认所有权的本地设备 | 提供中继/查询，不自动接管 |

独立单机与某门店的“失联副POS”不同：独立单机可以是该门店唯一主POS；失联副POS不能因为有长期token就获得共享订单的写入权。

### 失联副POS的默认降级

- 可查看已缓存目录、自己的未提交草稿、历史快照，并明确数据更新时间。
- 暂停共享桌台开台、既有账单收款、并台拆单、共享库存调整及授权范围变更。
- 如门店要求继续营业，可增设“独立临时单”：终端唯一编号、不占共享桌台，只接受允许的本地结算；恢复后单独导入，不自动并到旧账。
- 临时单属于可选业务扩展，必须先明确库存配额、现金责任及对账方式。长期离线授权不自动开启该能力。

若以后需要失联副POS继续修改特定订单，应提前发放独占所有权租约，并禁止其他节点在租约有效时接管同一订单；不能仅凭“终端曾经打开过这张桌”判断所有权。

## 3 主副POS管理与主节点故障

### 3.1 设备与配对

设备具备稳定`deviceId`、本机密钥对、门店、角色、名称、版本与授权状态。角色至少包含Coordinator、POSClient、KDS、PrintGateway；角色与员工角色分开。

主POS展示短时一次性配对码/二维码，副POS扫描后校验门店及主POS公钥指纹，双方确认，建立门店范围的设备身份。发现可用mDNS/服务广播，仍保留IP/主机名手工连接；发现结果本身不是信任依据。局域网通信采用认证加密通道，不能因同Wi-Fi就默认可信。

主POS设备页管理：设备列表、在线状态、最后同步、版本、角色、配对审批、停用与移除。副POS停用后保留历史业务归属。设备身份不能共用主POS的私钥或共用一条无限期token。

### 3.2 命令确认

副POS生成commandId与baseRevision，先本机落盘待发送，再提交主POS。主POS在同一事务中完成授权、版本校验、业务变更、事件与任务队列写入，成功后返回权威revision。副POS收到确认才显示“主POS已接收”，本机保存不等于门店提交成功。

两个副POS同时开同一桌，仅一个成功；冲突方刷新桌台。加菜采用独立行/命令ID；同一行改量、退菜、结账等按版本控制。支付、折扣和库存不采用“最后写入覆盖”。

### 3.3 接管与双主防护

记录`coordinatorId + authorityEpoch`；客户端、KDS与打印网关拒绝已知旧epoch的写命令。epoch必须由明确的权威程序提升，不能各设备自行加一后竞争。

首期建议人工接管，不承诺自动高可用：

1. 确认原主已停止经营并隔离其写入/出单路径。
2. 校验新主备份的已提交序号；缺失未复制数据时展示恢复点与可能缺口，不声称无损接管。
3. 由云端或预先设计的本地仲裁机制授予新epoch，重新分配设备连接及任务所有权。
4. 原主恢复后进入只读恢复状态，先上交未同步记录，由新主/云端对账后再加入。

仅一主一副、无云且无法确认旧主是否停止时，不能安全自动选主。即使客户端能识别旧epoch，网络分区中尚未知新epoch的旧客户端仍有双主风险；无法隔离/仲裁时暂停共享订单操作，不能仅靠心跳超时强行接管。后续自动选举需独立的多数仲裁与持久日志方案。

## 4 打印机与厨房屏

### 4.1 统一设备管理

新增“系统管理 → 门店设备”，包括打印机、打印网关、厨房屏、POS终端和任务中心。

| 打印机资料 | 厨房屏资料 |
| --- | --- |
| 稳定设备ID、名称、连接类型、IP/端口或配对标识 | 设备ID、档口、设备身份、显示布局 |
| 绑定网关、厂商/型号、能力、票宽、编码、切刀/钱箱支持 | 订阅菜品范围、优先级、提示音、超时阈值 |
| 用途：厨房/前台/结账/退菜单/交班 | 接单、制作中、出餐、挂起、取消状态 |
| 路由规则、联数、备机、状态、测试打印 | 心跳、游标、离线时长、最后接收序号 |

USB/蓝牙打印机由实际连接的主POS或网关独占访问；副POS只创建逻辑任务。网络打印机也只能有一个当前出单所有者，不能让每台POS各自直接重试。

### 4.2 档口路由与幂等

送厨批次在主POS持久化后，按菜品/分类/出品档口及路由版本生成任务：`eventId + stationId + ticketType + revision`组成逻辑唯一键。任务同时保存菜品名称、SKU/套餐替换、备注、数量、退赠标记等快照；后续改菜单不重写已提交厨房单。

路由策略可选“打印”“KDS”“两者都要”“KDS失败后人工转打印”。策略及交付条件须明确到档口。例如两者都要表示两个目标均被持久化接收；只有KDS时不因纸质打印机离线阻止送厨。

补打是新的执行尝试，保留原逻辑任务引用并标记补打、人员和原因。自动故障转移只针对明确未提交给设备的任务；结果未知时先查询或人工确认，避免备机重复出单。

### 4.3 打印状态

`待调度 → 网关已持久化 → 发送设备中 → 已发送待核对 / 已确认完成 / 失败 / 结果未知`。

驱动支持明确回执时才显示相应确认级别。TCP/USB写入成功只说明发送成功，不证明纸张实际打印。传统打印机不提供可查询jobId时，不承诺物理“恰好打印一次”；设备断线/应用崩溃后的不确定任务进入人工核对，不无限自动重打。

补打、缺纸、卡纸、断连、切刀错误等显示在任务详情；设备移除/改绑须处理旧网关未确认任务，不能把未知状态一键标成失败后重派。

### 4.4 KDS状态与恢复

KDS先持久化Inbox再确认接收；界面出现、厨师接单、制作中、出餐及前台已上菜为不同状态。KDS命令携带ticketId、commandId和baseRevision，由主POS确认后广播；不能靠本机UI点击直接覆盖其他档口状态。

重连先补齐主POS快照/增量，再订阅实时事件。重复投递不新增卡片；迟到的制作命令不得恢复已取消菜品。退菜单/数量减少用更高revision的事件展示明显变更，已完成任务保持可追溯。

仅KDS失联时，本机可缓存操作并显示“未获主POS确认”；恢复后逐条校验。KDS不直接结算、改价格或扣库存。档口落单失败不影响已成功接收的其他档口，前台看到部分成功及待处理列表。

## 5 注册 登录与离线授权

### 5.1 不能混用的凭证

| 凭证 | 签发方/用途 | 有效期草案 |
| --- | --- | --- |
| CloudAccessToken | 云端API访问，在线认证服务签发 | 15分钟（技术建议，待接口确认） |
| Refresh凭证 | 云端换取新访问凭证；只在云可达时生效 | 由身份服务策略决定，不赋予无限离线续期 |
| DeviceIdentity | 设备公钥身份、门店配对/通信 | 可轮换，撤销与业务授权分离 |
| OfflineGrant | 云端或授权激活服务签名，允许特定设备/员工/门店离线执行特定能力 | 短期7天、长期90天（用户已确认的默认值，可配置） |
| LanSession | 主POS为已配对设备/员工建立的局域网会话 | 例如8小时，不能晚于父OfflineGrant截止时间 |
| LocalSession | 本机验证身份后建立的应用会话 | 例如12小时，不得超出离线授权截止时间 |

“离线可用”需要验签授权凭证、有效角色及本机身份验证，不是让云端AccessToken永不过期。长期授权是显式批准的离线期限/能力策略，不能通过每天重新登录无限延长。

### 5.2 注册/激活路径

**首次可联网注册（默认路径）**：完成商户/账号注册与必要验证 → 建门店及设备身份 → 用户选择主POS → 云端签发设备绑定OfflineGrant并下发授权公钥与门店资料 → 本机事务保存 → 后续离线登录使用缓存身份与有效授权。

**门店已有主POS，副POS无公网**：副POS生成本机密钥 → 与主POS配对 → 主POS在已有云端授权明确允许的设备数量/角色范围内登记副设备并签发短时LAN委托会话。子凭证必须携带可验证父授权链、深度与能力限制；主POS不得扩展父凭证权限或有效期。若父授权不允许离线增加设备，则只允许已登记设备重新登录。

**首次完全离线开店**：

- 有预签发激活包：管理员从其他联网设备取得绑定目标设备公钥、门店和期限的签名包，经二维码/文件导入，验证后完成离线激活。
- 无任何可信授权材料：仅能建立“本地待认领门店/账号”，不能宣称已完成云端注册或云端商户唯一性校验。可否允许其正式营业及额度属于产品策略；默认提供演示/配置能力，正式营业需明确批准。
- 后续认领保留临时ID、原始事件及映射，不直接把本地财务记录删除或改写成另一个商户的记录。

### 5.3 短期/长期离线权限

| 项目 | 短期离线 | 长期离线 |
| --- | --- | --- |
| 获取方式 | 注册/正常登录后按策略预签发 | 门店管理员显式申请/激活，绑定设备与角色 |
| 基本营业 | 授权内开台、点餐、本地送厨、允许的本地收款 | 同左，要求更完整的本地备份、对账和设备管理 |
| 高风险操作 | 按缓存权限，必要时主管本地确认 | 限额/频次/角色更明确，不因期限长而权限更宽 |
| 云券/跨店储值/线上支付 | 无权威核验时禁用 | 同样不自动放开；除非另有可验证离线资产配额 |
| 续期 | 联网重新核验后签发 | 联网或导入新签名激活包；本机自行续期无效 |
| 到期 | 保留查询、导出与已提交任务核对；暂停新营业写入 | 同左；如需应急宽限，预先签发限定范围凭证并审计 |

员工离职/设备丢失的撤销不能在完全断网节点立即生效，这是离线授权的固有限制。最长离线期限就是最长暴露窗口的一部分；登录本地拒绝清单、联网立即撤销与设备隔离需共同设计。

### 5.4 凭证与时间保护

OfflineGrant建议含：`iss/sub/aud/jti/iat/nbf/exp`、tenantId、storeId、deviceKeyThumbprint、roles/scopes、policyVersion、authEpoch、offlineUntil、委托范围/深度/设备限额。主POS验证下属凭证链，副POS验证主POS设备身份，彼此不能只验证“token能解析”。

验签限定受信算法和issuer/audience，拒绝不符合令牌类型的凭证互用；相应原则来自[JWT安全实践RFC8725](https://www.rfc-editor.org/rfc/rfc8725.html)。具体JWT/JWS算法与密钥轮换由身份服务确定，不把自定义离线凭证描述为现成OAuth标准能力。

设备私钥建议使用[Android Keystore](https://developer.android.com/privacy-and-security/keystore)管理，签名时材料保持在受控容器内；是否硬件保护需按目标设备验证。设备绑定还应验证请求方持有相应私钥，仅在token里填一个deviceId不能防复制。在线OAuth持有证明可参考[DPoP RFC9449](https://www.rfc-editor.org/rfc/rfc9449.html)，局域网离线握手仍需独立规定挑战、防重放及验证流程。

缓存最近可信服务端时间、当前启动的单调时钟锚点及已知最大授权版本，检测明显回拨。设备离线重启后缺少可信时间来源时，不能宣称可绝对防回拨；异常时降权/要求管理员激活或联网校时。不要只用可手改的系统时间签发长期续期。员工本地密码/PIN验证与离线授权分开，凭据不写日志；现有演示哈希与公开主管不得直接作为生产身份系统。

## 6 同步节点与业务完成条件

同步节点不是“有网就全量覆盖”，而是三个不同链路：副POS↔主POS、主POS↔厨房设备、主POS↔云端。完整触发与确认矩阵见[同步节点与事件契约](同步节点与事件契约.md)。

建议拆开订单状态：

- `localCommit`：当前终端已保存。
- `storeCommit`：门店协调节点已事务接收。
- `kitchenDelivery`：每个必需目标的接收/失败/未知状态。
- `cloudSync`：待传、云确认、冲突、待人工处理。
- `paymentState`：本地记账或渠道处理中/成功/失败/未知，不与云同步状态混用。

因此“云端未同步”不应自动等于“厨房未收到”。本方案建议在门店已提交且必需厨房目标达到配置交付条件时，允许现金/经过确认的本地记账结账，即使云端暂不可达；这是对当前queued阻止结账规则的拟议升级，需要在实施前确认。

若厨房交付失败，可在有权限时明确选择“取消送厨”“修复后重送”或“人工交付已核对”，记录原因与人员；不能默默忽略。线上支付仍以支付渠道结果为准，第三方券和跨端余额不因本地授权有效就可离线扣减。

## 8 实施分期与待确认项

1. **本机基础**：事务化存储、事件ID/版本、完整Outbox/Inbox、分别持久化订单/厨房/云状态。
2. **设备与厨房单机闭环**：一个主POS、本地/网络打印网关、一个KDS、路由及不确定任务处理。
3. **局域网多POS**：配对、主节点命令处理、并发冲突、断线重连、手工接管边界。
4. **注册与授权**：云端签发、缓存公钥、离线登录、短/长期Grant、导入激活包及设备绑定。
5. **云端同步与真实支付**：增量游标、幂等接收、对账、后台配置版本、资产/支付结果查询。
6. **故障与现场验证**：断公网/断局域网/主POS关机、缺纸、KDS重启、授权过期、断电恢复和跨版本升级。

已确认：离线授权默认短期7天、长期90天，保留可配置能力。

待业务确认：到期宽限范围、完全离线首次注册的营业权限、失联副POS临时单、主节点备用硬件、厨房交付条件、支付方式/离线资产额度、打印机与KDS型号及同时使用台数。

本轮不因缺少这些参数而停止整理；除已确认的离线授权默认期限外，文中的其他期限、拓扑和降级规则均为可评审建议，尚未当成已批准的生产策略。
